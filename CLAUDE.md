## Build and Development Commands

```bash
npm install            # Install dependencies
npm run dev            # Start Vite dev server (port 5173)
npm run build          # Full production build (Te Araroa sync + climate + trails + TS compile + Vite)
npm run build:trails   # Build trail pages from data/trails/
npm run build:mobile-trails # Build the app's bundled trail JSON (mobile/assets/trails/)
npm run publish:trail-data  # Publish mobile trail JSON + catalog to R2 (--dry-run, --check, --all, --force, --remove <id>)
npm run sync:te-araroa # Copy the Te Araroa route out of the te-araroa-data package
npm run fetch:climate  # Fetch climate data for trail locations
npm run fetch:elevation # Fetch elevation data
npm run build:tiles    # Build map tiles
npm run fetch:fonts    # Fetch font glyphs for map labels
npm test               # Run all tests with Vitest
npm test -- --watch    # Watch mode
npm run lint           # Run ESLint
npm run preview        # Preview production build locally
```

## Git Workflow

**Rebase and merge is the only merge method allowed in this repo.** A PR lands on `main` as a linear run of its own commits, so a branch must never contain a merge commit. To pick up `main` or resolve conflicts, rebase the branch onto `origin/main` (`git rebase origin/main`, resolve each commit, then push with `--force-with-lease`) — never `git merge main` into the branch. A merge commit on a branch cannot be rebase-merged and has to be unpicked afterwards, which is far more work than rebasing in the first place.

## Architecture Overview

**Trail Maps** is a TypeScript web application for displaying Australian long-distance hiking trails with interactive maps, elevation profiles, and waypoint data. The repo also contains **Tracknotes**, the companion Expo/React Native mobile app (`mobile/` — see Mobile App section).

### Core Library (`src/lib/`)

Shared processing modules (used by both web and mobile):
- `distance.ts` - Haversine distance calculations
- `gpx-parser.ts` - Parse GPX XML into structured data; `parseGpx(xml, adapter?, limits?)` is platform-neutral (see XML adapters below) and parses coordinates strictly (throws instead of plotting 0,0)
- `xml-adapter.ts` - Minimal XML node interface (`querySelectorAll`/`querySelector`/`childElement`/`getAttribute`/`textContent`, tag selectors only) + the DOMParser adapter. `querySelector` searches every descendant, so a field that must be the element's *own* (`<wpt>`'s `<name>`/`<type>`, not its `<link>`'s) goes through `childElement`
- `xml-adapter-fxp.ts` - fast-xml-parser adapter (the React Native path — Hermes has no DOMParser)
- `gpx-optimizer.ts` - Track simplification (Douglas-Peucker), elevation spike removal/smoothing, elevation stats
- `track-simplify.ts` - Target-point-count simplification + coordinate truncation (the mobile point budget)
- `track-classification.ts` - Classify main/alternate/side-trip/**terminus** tracks. A `terminus` (`terminusPatterns`, default `['^Terminus:', '\\bTerminus\\b']`, collected into `terminusTracks`) is an *alternative trail end*: it branches off the main line at one end and its other end is deliberately free, 10-31 km off the route (the CDT's Chief Mountain, Columbus and Antelope Wells). It is matched **after** alternate and side trip, so a track a trail already names `Alternate: …` keeps that class. Several main tracks are normally chained by `combineTracksGeographically`, which orders them by proximity and bridges every join. A trail whose `trackClassification.stretches` is set instead uses `concatenateStretches`, which keeps the file's order and records any join wider than `minGapMeters` as a **route break** — somewhere the walking route genuinely stops and resumes (a ferry, an unbridged river). Opt-in per trail: turning it on for a file whose tracks are not in walking order would silently reorder the route
- `route-breaks.ts` - Reading those breaks back out for anything that draws the route (`splitAtRouteBreaks`, `routeBreakCrossings`). Breaks leave `track.points` a single flat array — every other consumer wants one ladder of cumulative distance — so only line-drawing code needs this. Used by both maps: the web viewer's `drawMainRoute` and mobile's `buildTrailLine` (a MultiLineString, one stretch per line). Anything that draws or climbs *part* of the route uses the other two: `sliceAcrossRouteBreaks` (the plan page's day lines, mobile custom-route spans) and `routeBreakStarts`, the index set the elevation helpers take so a ferry's landing-to-landing height difference is never climbed
- `waypoint-classifier.ts` - Classify waypoint types (town, hut, water, etc.). Five tiers: CalTopo folder → `KNOWN_TOWNS` → name prefix (`C:`/`WT:`…, delimiter required) → `KEYWORD_RULES` word matching → `waypoint`. The keyword tier is opt-in (`inferFromKeywords`) and is **on for user imports, off for the curated build** — guessing types for curated trails would churn `public/data/generated/*.json` for no gain
- `waypoint-taxonomy.ts` - The waypoint type vocabulary (`WAYPOINT_TYPES`, `WAYPOINT_TYPE_LABELS`, `waypointTypeLabel`) and the water/resupply family predicates (`isWaterWaypoint`, `isResupplyWaypoint`, `matchesWaypointFamily`). These predicates are the single home of rules that used to be duplicated across `water-carry-calculator`, `day-calculator` and `resupply-calculator`; they also accept the type aliases real-world GPX uses (`spring`, `supermarket`, …), which our own classifier never emits
- `trail-types.ts` - Shared `ProcessedTrail` / `TrackData` / `EnrichedWaypoint` / `RouteVariant` / `TrailConfig` — the shape of `public/data/generated/{id}.json`. `RouteVariant.type` is `'alternate' | 'side-trip' | 'terminus'`; **termini live in `sideTrips`**, not in an array of their own — every consumer of that list already means "routes that leave the trail and do not come back", so one array keeps the map lines, camera bounds, datasheet, reversal, mobile slimmer and handoff parser working unchanged, and anything that must tell them apart reads `type === 'terminus'`. A terminus has exactly one junction (`startDistance`, at `points[0]`) and never an `endDistance`
- `trail-ingest.ts` - `buildTrail(gpx, options)`: the whole GPX → `ProcessedTrail` pipeline (route selection, cumulative distance, display simplification, waypoint enrichment, variant junctions, off-trail split), with hooks for the build script's file-system/registry concerns. `track.displayPoints` aims at `DEFAULT_TARGET_DISPLAY_POINTS` (3,000) but `calculateAdaptiveTolerance` is capped at `MAX_TOLERANCE_METERS` (25 m), so a long trail overshoots that target rather than losing the shape of its line — the CDT keeps ~21,000 display points instead of drawing as straight chords beside its full-resolution alternates. A route break adds neither distance nor climb, is simplified around rather than across, and is published as `track.breaks`. **Waypoint km must stay on the track's own scale**: `enrichWaypoints`/`calculateSegmentStats` take the break indices and skip the same legs, or waypoints drift past the end of the trail they are measured along. **Variants read forwards**: `findVariantJunctions`/`attachVariantsToParents` turn a variant round (points reversed, ascent/descent swapped) when its source track was drawn against the trail, so `points[0]` is always the branch point at `startDistance`. Variant waypoint km and a child alternate's km along its parent both count from `points[0]`, so never swap the junction pair without reversing the points
- `gpx-import.ts` - `importGpx(xmlText, options)`: runtime import for user-supplied GPX (elevation cleaning on, `u_`/`uw_` synthetic ids, `ImportReport`). The user-facing spec of the pipeline is `docs/gpx-import.md` — keep it in step with behaviour changes here and in `trail-ingest.ts`. It is rendered into the site as `how-import-works.html` at build time (the `gpx-import-doc` plugin in `vite.config.ts`)
- `elevation-backfill.ts` - Open-Elevation backfill for GPX without `<ele>` (`backfillElevation` batches of 100, ≤2000 samples interpolated by distance; `applyElevation` re-derives ascent/waypoint stats via `recomputeTrailElevation`); `trailHasElevation`/`trailElevationIsUsable` drive the "distance-only estimate" labels
- `community-types.ts` - Wire contract for **community routes** (spec: `plans/community-routes.md`): `c_` ids (`isCommunityRouteId`), statuses `unverified`/`verified`/`hidden`/`removed`, `CommunityRouteSummary`/`CommunityRouteDetail` (`hiddenReason` for the owner/admin of a hidden route; `statusNote` admin-only), the AI review shape, report reasons, `COMMUNITY_LIMITS`
- `community-checks.ts` - `runCommunityChecks(trail, {name, description, gpxText?})`: the automatic checks for a shared community route — shape, length, points, distance-consistency, speed, elevation, gaps, metadata, waypoints. Run by the clients before upload and again by the worker, whose result counts. It never trusts its input. Coordinates, elevations, names, text and waypoint `trackIndex` are validated and kept; a `trackIndex` whose point is beyond `buildTrail`'s match radius of the waypoint (500 m route, 200 m variant) is re-placed as an import would place it (nearest point in range, else off-trail). Everything derived is rebuilt from that geometry the way `buildTrail` builds an import: point `dist`, length, `displayPoints` (Douglas-Peucker, budgeted, stride fallback), climb (3 m hysteresis), waypoint km/legs/climb, off-trail `distanceFromTrail`, and variant length, climb, junctions and `parent`. A variant must start within 500 m of the route or an attached alternate. Route breaks, POIs, `cumAscent`/`cumDescent`, timestamps, climate and the client's direction labels are dropped. The client's own km survive only for `distance-consistency`. The result is returned as `trail`, with `stats` for the row (`waypointCount` counts main, off-trail and variant waypoints). `speed` reads the raw GPX through `gpxMovingSpeedKmh` (a string scan, null under 10 timed points) and passes with a note when there is none. O(n log n) on real tracks; messages are plain English for the person sharing. OSM POI density is deliberately not a check — it varies by trail
- `trail-regions.ts` - Countries (ISO alpha-2) and their state/region codes, `LENGTH_BANDS`, and `matchesFilter`/`sortTrails`/`groupTrails` (Country → State, first state wins, "Other" last). Shared by the web landing page, the app's My Guides and the community forms. `trail.json` carries `country`, `states` (route order) and an optional `featured`; `scripts/trail-regions-data.test.ts` enforces them. The web and mobile `index.json` and the R2 trail catalog carry them, the per-trail mobile JSON does not (`stripListOnlyConfig`), so a list-only edit never moves a trail's md5 or triggers an over-the-air download
- `trail-handoff.ts` - `<slug>.tracknotes.json` web → mobile handoff format (`wrapTrailForHandoff`, strict `parseHandoffJson`)
- `poi-display.ts` - The platform-neutral half of showing OSM POIs, shared by the web viewer and the app: category labels, `poiDisplayName`, `summarisePoiTags` (+ the `safeHttpUrl`/`safeTelUrl` guards every POI link must pass), `slimPoi` (what `build-mobile-trails.ts` and the mobile import store write), the `PoiFilterState` shape and its normaliser, `visiblePois`/`countPoisByCategory` (both skip `duplicateOf`), `interleavePoisByDistance`, `mirrorPoiDistances`, and the slash-free `poiRouteKey` (`type-id`) that names a POI in an Expo Router param. `src/web/trails/trail-pois-ui.ts` re-exports it and keeps only the HTML/`localStorage` half
- `text-links.ts` - `splitTextLinks`: free text → plain/link segments, every `href` through `safeHttpUrl` (http(s) only). Waypoint descriptions carry bare URLs (Shikoku's henro.org pages); the app's waypoint detail screen renders them with `mobile/src/features/guide/LinkifiedText.tsx`, which opens a tapped link in the phone's browser
- `poi-noise.ts` / `poi-dedup.ts` / `poi-urban.ts` - The build/import-time passes between a raw `pois.json` and the shipped `pois` array: drop category-wide noise, flag POIs that duplicate a curated waypoint, thin city stretches (see `pois.json` under Trail Data)
- `point-index.ts` - Uniform-grid nearest-point lookup (`buildPointIndex`, `PointIndex.nearest`) in raw degree space, for answering "which track point is under the cursor?" without scanning a 20,000-point display copy on every mousemove. Platform-neutral, so the mobile map can reuse it; the web trail viewer rebuilds its index wherever `displayPoints` is set
- `types.ts` - TypeScript interfaces
- `plan-types.ts` - Plan data types shared with mobile. `PlanDocument` (id-keyed stops with `nights`, `note`, `booked`; `PLAN_LIMITS`) is the one plan shape: the wire body of `PUT /v1/plans/:id`, mobile's `plans.document_json`, the web `localStorage` value and the shared-plan payload. `PlanState` is legacy, read only by the web migration
- `plan-editor.ts` - The pure plan editor both platforms drive (spec: `plans/day-planner.md`): `toggleStop`, `replaceStopsInRange` (applying a suggestion), `setNights`/`setStopNote`/`setStopBooked`, start date and direction, `overnightCandidates`, `computePlanDays` (nights cascade into dates and `restDays`), `splitUnplannedTail` (the stretch after the last stop is "not planned yet" until it fits in a day), `servicesAtStop` over the trail's OSM POIs (1 km, `duplicateOf` included, `undefined` when the trail has no POI data), `migratePlanState`, `isPlanDocument`. Every editor returns a new document or the same object for a no-op; stop km stay NOBO-absolute
- `plan-alternates.ts` - Taking a trail's alternates in the day planner (spec: `plans/day-planner.md` "Alternates"). `buildPlannedRoute`/`plannedRouteTrail` splice the chosen alternates (`PlanDocument.alternates`, by name; only `type: 'alternate'` with both junctions and no `parent` — `plannableAlternates`) into the main line, giving a trail of the same shape in **route km**, so every planner calculator runs on it unchanged. The document keeps its km contract: a main-route stop is NOBO main km, a stop on an alternate carries `alternate` and the alternate's own absolute km (branch km + km along it). Both planners hold the stored document and edit a route-km view of it (`planToRoute`/`planFromRoute`, `editPlanOnRoute`); a stored stop the view cannot show is carried back unchanged when `planFromRoute` is given the stored plan, so always pass it; `setPlanAlternate` is the one edit that changes the route (drops overlapped alternates and bypassed stops, moves a stop whose waypoint id both lines share). `alternateMarkers` places the Stops list's branch/rejoin cards. One stop per place is checked per line, client and server
- `day-suggest.ts` - `suggestDays`: the N best alternative plans for the next K nights from a km, over caller-supplied candidates. It runs a k-best DP ranked by mean squared, range-scaled deviation from distance/ascent/hours targets, and a final walk out to the range end is held to maximums only. The criteria are the hiker's: `assertSearchable` refuses a set with no maximum rather than capping it. Both planners use it: the phone's Next days card and the web plan page's "Plan the next few days" section
- `plan-suggest.ts` - What both planners put around `day-suggest`, so they cannot drift:
  - the hiker's inputs (`SuggestPrefs`: mode, days, options, distance/ascent/hours ranges), their pace-derived starting values (`defaultSuggestPrefs`) and shape check (`isSuggestPrefs`);
  - the two modes as criteria (`suggestionCriteria`);
  - where a suggestion starts (`suggestionStart`: location, else last stop, else section start);
  - `applySuggestedPlan`;
  - the hour bands: `planWindowHours`, `planFloorHours`, and `finalDayMaxHours`, the most hours a plan's last day may take before it is "not planned yet".
- `track-geometry.ts` - Nearest-point lookup and elevation gain/loss between km positions. `calculateElevationBetween` (and `buildTimeIndex` in `day-calculator.ts`) take an optional `breakStarts` set — pass `routeBreakStarts(track.breaks, 'points' | 'displayPoints')` for whichever array you hand them, or a trail with route breaks climbs the gap between landings. When the points carry `cumAscent`/`cumDescent` (`annotateCumulativeElevation`, written into the mobile assets before thinning) both read the difference of the two ends instead of walking the steps between them, and `breakStarts` is not consulted — the break step was already left out of the sums. Summing a thinned track's own steps reported 65-86% of its real climb
- `day-calculator.ts` - Hiking time estimation and day splitting; `buildTimeIndex` reads the points' `cumAscent`/`cumDescent` when they carry them, so it keeps matching `calculateElevationBetween` to the metre on thinned and full-resolution tracks alike
- `resupply-calculator.ts` - Town resupply point calculations (incl. food carry weight); which waypoints count comes from `isResupplyWaypoint` in `waypoint-taxonomy.ts`
- `water-carry-calculator.ts` - Water carry distance calculations; which waypoints count comes from `isWaterWaypoint` in `waypoint-taxonomy.ts`
- `resupply-plan.ts` - Resupply *planning*: `resupplyCandidates` (the main route's waypoints plus every town a **side trip** leads to — on the side trip, or an off-route town within 1 km of its far end — offered at the junction with the side trip's length as `offTrailKm`, `accessMode: 'foot'` and its climb in `accessRoute`; call sites pass `resupplyCandidates(trail)`, never `trail.waypoints`) → `listResupplyOptions` (every resupply-family waypoint, grouped by the turn-off you leave the route at) → `resolveResupplyStops` (the ticked ids → stops; `undefined` = every option) → `computeResupplyLegs` (real ascent, Naismith hours, days, food per leg; **requires** `dailyHours` and `baseKmh` and throws rather than defaulting them). Each stop carries its `access` (`StopAccess`: the longest *walk* among its ticked places, else the longest ride), and a leg walks out of the stop it starts at and into the one it ends at: `distanceKm` stays trail km, `offTrailWalkKm`/`walkedKm` add the walk (in the hours, days and food), and `rides` lists the hitch/shuttle/boat km — and a distance whose way the data does not give (all of Te Araroa's) past `WALKED_WHEN_UNSAID_MAX_KM` (5 km; shorter unsaid ones are walked) — which are reported, never timed. `resupply-display`'s `legDistanceText`/`legRidesText`/`stopAccessText` are the shared wording ("52.3 km + 4.0 km off trail") → `summariseResupplyLegs`. Also `allResupplyOptionIds` and `plannedResupplyIds` (a ticked option plus the point on the route that serves it — the km the food has to reach — and *only* that point: at the CDT's Monarch Pass, ticking Salida must never plan Poncha Springs, the other town on the same hitch), which is what every mobile "planned" surface highlights
- `resupply-display.ts` - The platform-neutral text of a resupply option: `firstSentence` (abbreviation-aware), `accessSummary` and `resupplySummaryText`, each taking the caller's distance/weight formatter so the web (metric) and the phone (unit preference) share one set of words

**XML adapters:** GPX parsing is injected, not hard-wired, so one parser serves three runtimes. `parseGpx` defaults to `DOMParser` (web); build scripts pass `jsdomXmlAdapter` (`scripts/lib/xml-adapter-jsdom.ts` — jsdom must never reach `src/lib`); mobile passes `fxpXmlAdapter` (`src/lib/xml-adapter-fxp.ts`). A parity test (`src/lib/xml-adapter.test.ts`) asserts the fast-xml-parser and DOMParser backends produce deep-equal `GpxData` for every fixture.

**Ingestion is shared, not forked:** `scripts/build-trails.ts` and `importGpx` both call `buildTrail`, so a GPX file produces the same trail in the build, on the web and on the phone. The build script keeps only what needs a file system: CalTopo GeoJSON, the CSV waypoint fallback, climate, curated descriptions, the `data/waypoint-ids.json` registry, and HTML generation — each passed in as a hook. Any change to `trail-ingest.ts` must leave `public/data/generated/*.json` byte-identical unless the change is intentional.

**Shared calculators:** `track-geometry.ts`, `day-calculator.ts`, `resupply-calculator.ts`, `resupply-plan.ts`, `resupply-display.ts` and `water-carry-calculator.ts` are the single implementations used by both web and mobile. Mobile imports them via the `@lib` alias (Metro `watchFolders` + tsconfig paths + Jest `moduleNameMapper`). Parameter types are structural (e.g. `PlanWaypoint`, `PlanStopInput`) so each platform's own trail/waypoint/stop shapes are accepted without conversion. On mobile the Plan screen edits a saved `PlanDocument` through `@lib/plan-editor` (SQLite `plans`, `state/plans-store.ts`); nothing writes stops on its own. The Next days card (`features/plan/NextDaysCard.tsx` + `plan-suggest.ts`, over `@lib/day-suggest`) offers ranked alternatives for the next few nights from the GPS km or the last stop, by hours & pace or by distance/climb/hours ranges (per-trail inputs in `plan-inputs-store` `suggest`). Applying one replaces only the stops inside its window. Pace and daily hours stay per trail in `plan-inputs-store.ts` (device-local, not part of the document — a shared plan should not say how fast its author walks); the resupply selection is `PlanDocument.resupplyStops`, edited through `setResupplyStops`, with a legacy `plan-inputs-store` selection read only while the document has none. The adapters live in `mobile/src/features/plan/plan-adapters.ts`. Pace presets (`Pace`, `PACE_KMH`) live in `plan-types.ts` so the two platforms cannot drift.

### Build Scripts (`scripts/`)

- `build-trails.ts` - Generates static trail pages + `public/data/generated/*.json` from GPX/JSON data; the geometry work lives in `@lib/trail-ingest` (`buildTrail`) — this script only supplies the file-system pieces (config, CalTopo GeoJSON, CSV fallback, climate, curated descriptions, waypoint-id registry) and writes the output
- `build-mobile-trails.ts` - Builds mobile-optimized trail JSON (reduced points, truncated precision). A trail with route breaks is simplified one stretch at a time, so Douglas-Peucker cannot drop a break's boundary points and cut the corner across the water; `index` is re-anchored to the result, `displayIndex` is re-anchored the same way, because `displayPoints` is thinned here too: the web copy is no longer a fixed ~3,000 points (see `trail-ingest.ts`'s tolerance ceiling), so the phone clamps it to the same `TARGET_POINTS` budget as `points` — a line no coarser than the array it already ships, and no finer. Every point of both arrays also gets `cumAscent`/`cumDescent`, measured on the full-resolution track *before* thinning (`annotateCumulativeElevation`, skipping the step into each break) and rounded to whole metres: thinning keeps the shape of the line, not its ups and downs, so without them the phone's plans, ETAs and route stats under-counted climb by 14-35%. `processTrail` is exported and `main()` guarded so this is testable. `index.json` records each file's `md5`/`bytes`, and a trail's `updatedAt`/`dataVersion` move only when its md5 changes (the previous index is read back), because `updatedAt` is what the app orders over-the-air copies by
- `build-contours-australia.ts` - Builds contour PMTiles for the contour tile worker
- `build-contours-world.ts` - Builds world contour shards from Copernicus GLO-30 DEM, `--join` merges shards to world.pmtiles (spec: `plans/world-contour-tiles.md`)
- `fetch-dem-copernicus.ts` - Downloads Copernicus GLO-30 DEM tiles (global, anonymous, per bbox/cells/shard)
- `contour-experiment.ts` - Contour quality experiment harness: settings-matrix builds + side-by-side compare viewer (`npm run experiment:contours`)
- `lib/world-grid.ts` - Global 2° cell grid, shard partition, Copernicus tile naming
- `lib/trail-data-catalog.ts` - Pure helpers shared by `build-mobile-trails.ts` and `publish-trail-data.ts`: file digests, the `index.json` merge rule (keep `updatedAt` while the md5 is unchanged), the R2 catalog shape, content-addressed keys, validation, and the upload plan
- `lib/xml-adapter-jsdom.ts` - jsdom `XmlAdapter` for `parseGpx` (kept out of `src/lib` so jsdom never enters the mobile bundle)
- `remote/` - Remote-machine world build: bootstrap, detached shard driver, status, R2 upload (runbook: `docs/world-contours-remote-build.md`)
- `fetch-climate.ts` - Fetches historical climate data for trail locations
- `fetch-elevation.ts` - Fetches elevation data
- `fetch-pois.ts` - Fetches OSM POIs along each trail corridor via the shared `gpx-tools` library (`npm run fetch:pois [trail-id]`). Reads track geometry from `public/data/generated/{id}.json` (so `build:trails` must have run) and writes the results to `data/trails/<dir>/pois.json` — in the repo, where a rebuild cannot wipe them. `--endpoint <url>` / `OVERPASS_ENDPOINT` and `--timeout <seconds>` pick the Overpass instance; mirrors come and go, so try them in turn: `overpass.private.coffee` served the Australian trails (2026-09-08, `--timeout 120`), but by 2026-09-30 it timed out from a cloud session, where `overpass-api.de` reset the connection and `overpass.kumi.systems` timed out too. What answered there was `--endpoint https://maps.mail.ru/osm/tools/overpass/api/interpreter`, which drops any query past about 60 s, so it wants small cheap ones: `--max-vertices 60 --timeout 55` (or 150/120 for a lighter trail). A run that loses chunks merges what succeeded into the existing file instead of replacing it (so a whole-trail run can never ship a hole), prints which chunks failed and exits 1 — re-run it until no chunk fails (how the CDT's file was built); `--force-replace` writes the partial result as-is. On 2026-10-06 `overpass.private.coffee` answered again (`--timeout 120`, Shikoku in one 182 s query), but its data lagged: the same day `maps.mail.ru` (`--max-vertices 60 --timeout 55`) returned a 2026-09-21 survey of central Tokushima that it lacked
- `fetch-font-glyphs.ts` - Fetches font glyphs for map label rendering
- `build-tiles.ts` - Builds map tiles for offline use
- `e2e-tile-check.mjs` - Probes the deployed tile infrastructure through the URLs the app uses (`mobile/eas.json`): contour worker health and tiles, and an offline pack for **every trail in `mobile/assets/trails/index.json`** (manifest lists `base.mbtiles` and `contours.mbtiles`, each object present at the manifest size). `npm run check:tile-packs` runs only the pack check; the `tile-packs` workflow runs it when the bundled trail list changes and weekly, so a new trail fails CI until its pack is built (`build:tiles --trail <id>`) and uploaded (`upload:tiles <id>`)
- `build-grid-tiles.ts` - Builds grid-based map tiles
- `tile-pipeline.ts` - Orchestrates the full tile generation pipeline
- `process-heysen-waypoints.ts` - Trail-specific waypoint data processing
- `process-shikoku-caltopo.ts` - Builds `data/trails/shikoku/shikoku-t1-t23.gpx` (Shikoku Henro, Temples 1-23) from a CalTopo GeoJSON export of the whole island: keeps the purple "88 Temple Pilgrimage" line and every marker within 3 km, types each by its folder, and adds Temples 3-9 and the Shosanji Okunoin from OpenStreetMap. The export itself is not committed — a GeoJSON in the trail directory would be read as a category source keyed by folder names the classifier does not know. The Okunoin out-and-back is lifted off the route by `extractSpurs`, and `waypointMaxDistance` is 3000 m so pilgrim lodgings a short walk off the line stay on the datasheet and plan page. Places the map lacks (Sudachi-an and the other Temple 11-13 lodgings), closures and corrected descriptions are curated in the script itself (`CURATED_WAYPOINTS`, `CLOSED_MARKERS`, `DESCRIPTION_OVERRIDES`) and applied on every run; `--reapply` applies them to the committed GPX when there is no fresh export (the GPX round-trips through `parseGpx`/`generateGpx` byte for byte, so the track is untouched). ### Trail Data (`data/trails/`)

Each trail has its own directory containing:
- `*.gpx` - Original GPX track data
- `trail.json` - Trail metadata and waypoints
- `climate.json` - Climate data for locations along the trail
- `pois.json` - Optional OpenStreetMap points of interest along the trail, written by `fetch-pois.ts` and folded into the generated JSON's `pois` array by `build-trails.ts`. POIs are kept **separate from waypoints**: they are never merged into `waypoints` and never enter `data/waypoint-ids.json`. Shape: `{ source, attribution, fetchedAt, searchRadiusKm, endpoint, rejected, pois }`, where `pois` holds everything fetched (sorted by `distanceAlongTrail`, then key) and `rejected` is a hand-edited list of `<type>/<id>` keys the build drops. A re-fetch carries `rejected` over unchanged, so review work survives a refresh. The file is the raw fetch: three build-time passes sit between it and the shipped JSON — `@lib/poi-noise` drops category-wide noise (bus stops other than walkers' shuttles, picnic shelters and pergolas, hospitals tagged `emergency=no`, help phones on motorways and in road tunnels), `@lib/poi-dedup` flags POIs a curated waypoint already covers — matched against every waypoint the trail has (`dedupCandidates`: main route, off-trail, alternates, side trips and termini), and against a generic `poi`-typed one only when the two are within 10 m with the same name, and `@lib/poi-urban` thins cities: where POIs run over 15 per km of trail (seeded there, grown out through suburbs at half that, at least 40 POIs) it keeps only the first and last of each category, anything flagged `duplicateOf`, and "anchors" — supermarkets, convenience stores (Japan's resupply: the Shikoku henro's konbini), outdoor shops, post offices, campgrounds, huts, hospitals with `emergency=yes`, stations, ferry terminals — one per kind per 2 km, branded first. That took Te Araroa from 8,790 shipped POIs to about 2,100 (Auckland 3,166 → 50), and also thins Albany (Bibbulmun), Albury (Hume and Hovell) and Jackson (CDT); small trail towns stay whole. All three run at build/import time, never at fetch time, so changing a rule is a rebuild rather than another slow Overpass run. A trail can add rules of its own in `trail.json` `pois` (`TrailPoiConfig`): `exclude` drops OSM `key=value` tags that are no use on that trail (Shikoku drops `amenity=post_office` and `amenity=fuel`; a POI that is also `shop=convenience`/`supermarket` is kept), and `keepInCities` exempts a tag within `withinKm` of the route from city thinning (Shikoku keeps every konbini within 500 m: one per 2 km hid 19 of the 40 a pilgrim walks past in Tokushima). `build-mobile-trails.ts` ships them to the app slimmed through `@lib/poi-display` `slimPoi` (display tag keys only, rounded coordinates, no `duplicateDistanceM`). See `scripts/lib/trail-pois-file.ts`.
- `descriptions.json` - Optional curated waypoint descriptions, keyed by the stable ids in `data/waypoint-ids.json`. `build-trails.ts` applies them to the bundled trail JSON (overriding any GPX/GeoJSON text); `upload-descriptions.ts` pushes the same file to the comments API, where mobile syncs it as an override (`synced ?? bundled`). The prose is factual and non-prescriptive — it describes the place and its water, never instructs the walker or addresses them as "you". See `scripts/lib/waypoint-descriptions.ts`.

A trail may also carry `Terminus: <name>` tracks — alternative starts/finishes, declared with `trackClassification.terminusPatterns` and drawn junction-first, with a `<wpt>` of `<type>endpoint</type>` at the free end. `buildTrail` attaches the one junction at whichever end is actually nearer the route (turning the line round if the generator drew it backwards), attaches the nearby waypoints including that endpoint to the variant, and keeps the endpoint out of `offTrailWaypoints` so a place the route reaches is never also listed as a place it misses.

Te Araroa's file also carries waypoint types no other trail uses. `gap` is the "Trail ends"/"Trail resumes" pair at each route break. The **turn-offs** are points on the route at the km you leave it for a place that is somewhere else, typed `<servedType>-access` — `town-access`, `hut-access`, and so on — so one field says both what kind of place it is and that you are not there yet.

Two rules follow, both in `waypoint-taxonomy.ts`:
- `RESUPPLY_TYPES` lists `town-access`/`food-access`/`resupply-access` **one by one** rather than stripping the suffix generically. A `water-access` must never satisfy `isWaterWaypoint` — that would tell the carry calculator there is water on the route when it is down a side road, and under-reporting a dry stretch is the dangerous way to be wrong.
- `baseWaypointType()` is the fallback for every map keyed by type: `MAP[type] ?? MAP[baseWaypointType(type)] ?? FALLBACK` gives a turn-off its served type's icon, colour and chip without seven more entries per map. Use it rather than enumerating; `isAccessWaypoint()` is there for the cases where a turn-off must behave *differently* from the place (you cannot sleep at one — see `overnightWaypoints`).

Changing a bundled waypoint's `type` re-keys it in `data/waypoint-ids.json`, which matches on type + 100 m proximity: the ids churn silently and any server-side comment keyed to them is orphaned. Migrate the registry entries in the same commit. A waypoint whose exact name is on a nearby entry claims it before any proximity match, so a newcomer of the same type within 100 m of an existing waypoint mints its own id instead of taking that one's. An entry no waypoint matches in a build is kept but marked `retired: true`; a retired entry is reclaimed only by a waypoint of the same type, within range, with the exact same name, so a new place built near a removed one never inherits its id, comments or description.

**Te Araroa is not curated here.** Its route, waypoints and resupply points are built in [te-araroa-data](https://github.com/eamon-b/te-araroa-data), which commits its outputs; this repo takes them as a devDependency pinned by `package-lock.json`. `npm run sync:te-araroa` copies `te-araroa-sobo.gpx` out of `node_modules` into `data/trails/te_araroa/`, where it is gitignored — only `trail.json` and `climate.json` are committed. `npm run build` runs the sync first, so a fresh clone (or Vercel) builds without a manual step. `npm update te-araroa-data` takes a newer build. Do not hand-edit the GPX: it will be overwritten, and the fix belongs upstream.

**Open-data trails.** Eleven Australian trails come from open data rather than a guidebook, and each `trail.json` `dataSource` names its dataset and licence: the Great Ocean Walk and Great South West Walk from Great Trails Victoria (CC BY 4.0, waypoints included); the Overland, Three Capes and South Coast tracks from the Tasmanian LIST Transport Segments layer (CC BY 3.0 AU) with OSM waypoints; the Great North Walk, Six Foot Track, The Coast Track, Grampians Peaks Trail, Kep Track and Thorsborne Trail from OSM route relations (ODbL). Their `<ele>` is Copernicus GLO-30 sampled every 30 m and smoothed over five samples before it was written, because the build sums every delta and raw surface-model samples read forest canopy as climb (the Great South West Walk read +6,220 m raw, +3,400 m smoothed). The GPX files were generated once and are the source of truth here; the generator is not committed. Their waypoints have since been reviewed by hand (2026-10: towns and trail ends added, duplicates and non-public camps removed or retyped `poi`, names fixed), so a regeneration would lose that review — diff the waypoints against the committed file before replacing one. Where their climate locations sit off the trail's height (a river camp under a slope, a range crossing the terrain model smooths down, a coastal point on a sea cell), `climateLocations[].elevation` makes `fetch-climate.ts` correct the temperatures to that height.

### Comments API Worker: community routes (`workers/comments-api/`)

`src/community.ts` / `src/community-review.ts` (migrations `0005`, `0006`): D1 `community_routes` + `community_route_reports`. A submit re-runs `@lib/community-checks` (with the uploaded GPX as `gpxText`, for the `speed` check) and stores *its* rebuilt trail, never the client's JSON, with `config` rewritten server-side (id, name, `source: 'community'`, country/states, description, CC0 `dataSource`). The bucket has no private area (all of it is served at `PHOTOS_PUBLIC_BASE`), so private objects live at unguessable keys recorded in the row and never returned: the canonical trail JSON at `community/private/<id>/<32 random hex>.json` (`private_key`) and the optional raw GPX (≤ 5 MB) beside it as `.gpx` (`gpx_key`; a file whose head is not `<gpx` is dropped, not refused). While a route is live, a public copy of the same bytes sits at `community/v1/<id>.<md5[0..12]>.json` (`r2_key`; `max-age=300`, so an edge copy outlives a hide by minutes, not a year). An owner's edit writes new objects, keeps the public version it replaced (cached lists still name it) and purges older ones; a de-attribution purges the old public versions at once, since they name the deleted account; hiding a route (AI review, reports or admin) deletes every object under `community/v1/<id>.` and NULLs `r2_key`, so owner/admin detail of a hidden route has `trailUrl: null`; an admin restore from hidden always republishes from the private copy (if it is gone: 404 when removed meanwhile, 409 `conflict` when the row changed, else 500 `trail_missing`), and a hide re-reads the row after its purge and republishes a route a restore made live meanwhile; removal purges both prefixes. Every row change sets `updated_at` strictly later than the value it read (`stampAfter`); an owner's PATCH, an admin status change, a de-attribution and the AI review write only if `status`/`updated_at` still match the row they read — a lost race returns 409 `conflict` (PATCH, admin) or retries (de-attribution) and deletes the objects it wrote, and a stale review writes nothing (its verdict write leaves `updated_at` alone). `@lib/community-checks` rebuilds every distance and climb from the coordinates (point km, length, display points, waypoint and variant km, 3 m-hysteresis climb) and drops client route breaks, POIs and `cumAscent`/`cumDescent`, so no client-claimed distance or climb is stored. The duplicate hash is sha256 of the trail without its `config`, so a rename does not get past it (the 409 carries `existingId` only for the caller's own route; the near-duplicate warning names the other route by id); a body whose non-GPX part exceeds 4 MB + 64 KB is refused 413 `trail_too_large` before it is checked; the 10-a-day `communitySubmit` limit is spent only after the checks pass and the stored JSON measures ≤ 4 MB, `communitySubmitAttempt` (30 a day) is spent by every submit before its body is parsed, and `communityEdit` (20 a day) by every PATCH that changes something. The `claude-sonnet-5-5` review (structured output, `fallbacks: 'default'`, all route text fenced as untrusted) runs from `waitUntil` (SDK client with a 20 s timeout and 1 retry) and **fails open** — `skipped` without the `ANTHROPIC_API_KEY` secret (`wrangler secret put ANTHROPIC_API_KEY`), `failed` on an API error or refusal. The review also sees a bounded sample of waypoint descriptions, the variant names, and a sample of off-trail and variant waypoint names (≤ 200 names in all, at least 50 of them off-trail/variant when there are that many). A reject with confidence ≥ 0.8, or 3 distinct reports filed after the route's last admin status change (`status_changed_at`) by accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`; younger accounts' reports are stored but do not count), hides an *unverified* route; a verified one stays up and rises to the top of the admin queue. An owner's detail of a hidden route (`GET /v1/me/community/routes`, or `GET /v1/community/routes/:id` with their token) carries `hiddenReason` (`'review' | 'reports' | 'admin'`). It is derived from the hide's `status_note`: the review and report hides write the fixed `REVIEW_HIDE_NOTE`/`REPORTS_HIDE_NOTE`, and anything else counts as an admin hide. `statusNote` itself stays admin-only, and an admin note equal to either fixed note is refused 400 `invalid_note`. Only an admin verifies. Deleting an account de-attributes its routes (CC0) rather than removing them; `deattribute_pending` keeps that durable, and a Cron Trigger (`*/15 * * * *`, `runCommunityMaintenance` in `src/index.ts`'s `scheduled`) retries pending de-attributions and re-runs AI reviews left `pending` over 10 minutes. A PATCH re-runs the `metadata` check. Reports spend the `communityReport` bucket (20 a day) through `consumeRateLimit`. The public list and "my routes" are keyset-paged (`?cursor=` / `nextCursor`). A route an admin removed (or its owner deleted while an admin had it hidden) sets `blocks_resubmit`, refusing the same track again. Community ids are not in `ALLOWED_TRAILS`: no comments, descriptions or plan sync for them yet.

## Key Patterns

- **Build-time processing**: Trail data is processed at build time into optimized JSON
- **Static site**: All pages are pre-generated, no runtime server required
- **Client-side rendering**: Trail viewer loads JSON data and renders interactively
- **Web maps**: Leaflet with OpenTopoMap tiles for topographic display
- **The app informs the hiker's decisions; it never makes them.** Pace, hours per day, and any other figure that says how far or how long is "reasonable" is the hiker's input, not ours. A UI module must never fix such a figure in a constant (the web plan page's former `RESUPPLY_BASE_KMH = 4` / `DEFAULT_RESUPPLY_DAILY_HOURS = 8` are the named example, removed per `plans/resupply-mobile.md` Phase 0): give the page the input the phone already has, persist it with the plan, and feed the calculator from it. A *default* is fine only as the initial value of an input the hiker can see and change; a shared calculator should require the figure rather than silently substitute one. The same applies to thresholds that colour a judgement — "long carry", "dry stretch", grams of food per day — which are on the follow-up list to become inputs

### Key Expo Concepts

- **Continuous Native Generation (CNG)**: `ios/` and `android/` are generated from `app.json` + config plugins via `npx expo prebuild`. They are build artifacts, not source files. Regenerate with `--clean` after config changes.
- **Config plugins**: Declared in `app.json` `"plugins"` array. They modify native project files during prebuild (e.g. MapLibre adds location permissions automatically).
- **Development builds**: Custom debug apps built via EAS that include your native dependencies. Rebuild only when native deps change; JS changes hot-reload.
- **EAS Build profiles** (`eas.json`): `base` (shared env), `development` (dev client), `development-device` (dev client on a physical device), `preview` (internal testers — a standalone `.apk` you can sideload; how to build and install one is `docs/mobile-test-build.md`), `production` (app store — an `.aab`).
- **EAS Update**: OTA JavaScript updates. Not available in this app yet — `expo-updates` is not installed and `app.json` has no `updates`/`runtimeVersion` — so every change, JS included, ships as a new build.
- **Expo Router**: File-based routing where files in `app/` become navigation routes. `_layout.tsx` defines navigators, `(groups)/` organize without adding URL segments, `[param].tsx` for dynamic routes.

### Verification After Dependency Changes

When changes affect native dependencies (adding/removing/updating packages, modifying `app.json` plugins), verify with:
1. `npx expo prebuild` — ensures config plugins resolve and native projects generate correctly
2. `eas build --profile development --platform android` — ensures the development build compiles with the updated dependencies

### Common Gotchas

- Always `npx expo install` for Expo packages — ensures SDK-compatible versions
- Run `npx expo prebuild --clean` after changing `app.json` plugins — stale native config is the #1 debugging time-sink
- Clear Metro cache when things are weird: `npx expo start --clear`
- Only env vars prefixed with `EXPO_PUBLIC_` are available in client code
- Expo Router: `_layout.tsx` naming must be exact (not `Layout.tsx` or `layout.tsx`)
- Don't have both `app/foo.tsx` and `app/foo/index.tsx` — they conflict

### Mobile Environment Variables

`EXPO_PUBLIC_*` vars are inlined by Metro at bundle time from `mobile/.env.local` — **restart Metro after changing them** (hot reload won't pick them up). The env block in `eas.json` applies only to EAS cloud builds, NOT to local Metro bundles, so each var must also be in `.env.local` for local dev. All three are non-secret public URLs (they ship in the client bundle):

```
# Comments API (local wrangler dev server, or the deployed worker URL)
EXPO_PUBLIC_API_BASE_URL=http://localhost:8787   # deployed: https://api.contour-map-tiles.net

# Contour vector tiles — without this, online maps silently render without contours
EXPO_PUBLIC_CONTOUR_TILE_URL=https://tiles.contour-map-tiles.net

# Offline map tile downloads — without this, the Offline Maps screen disables downloads
EXPO_PUBLIC_TILE_BASE_URL=https://data.contour-map-tiles.net
```

### Mobile App Architecture

The app is named **Tracknotes** (`app.json` name/slug `tracknotes`, package `com.tracknotes.app`, URL scheme `tracknotes://`).

- **Map**: MapLibre React Native. Style objects are resolved before mount via `src/services/online-style-service.ts` (online) or `tileManager.getOfflineStyle()` (offline); the bundled base style is `mobile/assets/topo-style.json`, synced from `scripts/topo-style.json` with root `npm run sync:style`. Contours come from `EXPO_PUBLIC_CONTOUR_TILE_URL`, from the worker's `contours` (Australia) source for a trail inside that archive's bounds and its `world` source for every other trail (`contourSourceFor` in `online-style-service.ts`) — the Australia archive returns empty tiles abroad.
- **Map theme**: the map follows the app theme (`useTheme().isDark`), not a setting of its own. Dark is a *night topo*, not a separate style: `src/services/night-style.ts` repaints every layer of the light style — Liberty online, `topo-style.json` offline — by colour role (areas inverted into a dark band, lines compressed so roads stay lighter than the ground, text lifted, halos darkened, hue kept), so forest, parks, water, paths and relief survive in dark mode. (It replaced OpenFreeMap's Dark-Matter `dark` style, which drew a near-black map with none of them.) Offline, the paint patch `scripts/topo-style-dark.json` (also synced by `npm run sync:style`) is merged over the repaint for the layers it does not suit — today only the contours, whose ink matches the online contour layers; a test asserts every id in it still exists in the template. Overlay cartography (tracks, marker/label ink, the fallback style) is per-theme in `features/map/map-style.ts` — `trackColors(theme)` / `mapInk(theme)` — and the theme is part of `mapRemountKey`, because swapping a live map's style object can kill the native renderer.
- **Storage**: trail content is read via `src/services/trail-loader.ts` — there is no `trails` SQLite table. Sources: bundled JSON assets (the seed), newer copies downloaded from R2, catalog-only trails, community routes, and user imports. SQLite (`expo-sqlite`) holds per-guide state, comments + outbox, favorites, and custom routes. Tile files live in `expo-file-system`.
- **Over-the-air trail data** (runbook: `docs/trail-data-updates.md`): `services/trail-data-updates.ts` fetches `{EXPO_PUBLIC_TILE_BASE_URL}/trails/v1/catalog.json` on launch/foreground (`hooks/useTrailDataUpdates`, throttled to 6 h; My Guides pull-to-refresh forces it) and downloads newer content-addressed trail files to `{documentDir}/trail-data/` (size + md5 + shape checked on a `.part` file before `state.json` names it; `state.json` itself is written to a temp file and renamed into place). The pure rules are `services/trail-catalog.ts`: a copy replaces another only when its `updatedAt` is strictly later, so a newer APK beats an older download and unpublished build data is never reverted. A downloaded copy of a bundled trail makes the sync `getTrailJson` return null (callers fall back to async `loadTrail`); use `getBundledTrailJson` only where stale data is fine. Catalog-only trails (`source: 'remote'`) are listed from the last catalog, downloaded on first open by `GuideProvider` (or the shared-plan screen), and registered with `isServerKnown` via `registerRemoteTrailIds`. An open guide keeps the data it opened with until the hiker taps Reload on the banner it shows once a newer copy is installed (`GuideContext` `dataUpdate`, compared by `trailDataVersion`, the md5; `GuideUpdateBanner`); Settings → Guide updates forces a check
- **Community routes** (`c_…`, `TrailSource 'community'`): `services/community-routes.ts` caches `GET /v1/community/routes` in `{documentDir}/community/state.json`, refreshed alongside trail data (30-minute throttle, forced by pull-to-refresh), and downloads a route's `trailUrl` on first open with size, md5 and shape checks, and again when the list's md5 changes (owner edit, de-attribution). A list never deletes anything: it can be truncated, stale or briefly empty, so each downloaded route it leaves out is probed (`GET /v1/community/routes/:id`, no token, `no-store`, ≤ 20 per refresh) and only a 404 marks it `takenDown` — kept on the phone, shown as "No longer shared" in My Guides and the guide banner, cleared if a list names it again. Opening a route that 404s shows "This route is no longer shared" (no retry) and forces a list refresh. Long-press on a community card: About & report, Remove from this phone. Removing a route or the owner deleting it runs `services/local-trail-data.deleteLocalTrailData` (custom routes, favourites, waypoint_meta, comments/outbox/sync_state, plan, `plan-inputs-store`, direction, current-hike pin), the same cleanup an imported trail's delete runs. Pure rules in `community-catalog.ts` (`planCommunitySync`, `classifyCommunityProbe`); the client is `api/community.ts`. `isServerKnown` refuses `c_` as it refuses `u_` (`isLocalOnlyTrailId`), so a community route gets no comments, plan sync or descriptions, and borrows offline packs like an import. A hidden route is never in the list or My Guides; its owner finds it under Settings → My shared routes (`features/community/useMySharedRoutes.ts`).
- **Shared code**: `src/lib/` (repo root) modules imported via `@lib`. Currently used: format-distance, community-types, community-checks, trail-regions, comments-api-types, track-geometry, plan-types, plan-alternates, day-calculator, day-suggest, resupply-calculator, water-carry-calculator, distance, types, trail-reverse, trail-types, route-breaks, gpx-import, xml-adapter-fxp, poi-display. Every `src/lib` module is RN-safe: `gpx-parser`/`gpx-optimizer` no longer reach for `DOMParser` (mobile passes `fxpXmlAdapter`), and `gpx-import` avoids `crypto` entirely. jsdom stays out of `src/lib` — its adapter lives in `scripts/lib/xml-adapter-jsdom.ts`.
- **Navigation**: a single Expo Router Stack — "My Guides" list → per-trail guide (nested stack). No bottom tabs. Inside a guide, a segmented control switches three always-mounted panes: Map | Elevation | List (`src/features/guide/GuideView.tsx`).
- **State**: Zustand stores in `src/state/` (settings, downloads, favorites, identity, plans) plus per-guide React contexts. Per-trail pace and daily hours are in `features/plan/plan-inputs-store.ts`; the resupply selection is in the plan document (`state/plans-store.ts`), and `use-planned-resupply.ts` is the one source of "planned resupply" for the map, profile, list, detail screen and distance strip — `null` until a plan is made, and `null` means nothing is planned, never everything.
- **OSM points of interest**: bundled trails carry `pois` (slimmed by `build-mobile-trails.ts`), imported ones whatever the `.tracknotes.json` handoff brought (a GPX imported on the phone has none — the on-phone Overpass search is a follow-up, see `plans/pois-mobile.md`). POIs are never waypoints: they are not in the plan calculators, the GPS distance strip, favorites or comments, and `duplicateOf` entries are never drawn or listed (their OSM detail shows on the waypoint they duplicate instead). One global `poiFilter` in the settings store (master switch + six categories) drives every surface through `features/guide/use-visible-pois.ts`; the map's layers sheet edits it. Map markers are smaller, thin-ringed badges hidden below zoom 11; the List pane interleaves POI rows (an "OSM" pill) by km; the elevation profile draws hollow ticks only when zoomed to ≤ 60 km; `guide/[trailId]/poi/[poiKey]` is the detail screen. Direction reversal mirrors POI km inside `@lib/trail-reverse`, so nothing on mobile special-cases it.

### Mobile Source Structure (`mobile/src/`)

Feature-sliced: UI lives with its feature, not in a global components dir.

- `features/` — one dir per feature, each with colocated `__tests__/`:
  - `guide/` — GuideView shell, waypoint list pane (waypoint + POI rows; a `Resupply` pill and a `Planned` chip once a resupply plan exists), contexts (GuideContext, GuidePositionContext), direction toggle, distance strip (a `Next resupply` chip while a plan exists, never falling back to an unplanned town), `use-visible-pois.ts`

  - `plan/` — plan inputs card and `PlanSettingsSheet` (the settings behind the Plan screen's summary row), `plan-glance.ts` + `use-plan-glance.ts` (the plan's days over the whole route as planned — `use-plan-route`, alternates spliced in — and the days either side of one place) with `PlanGlanceSheet` (the map's ⛺ "View plan" button, shown once the plan has a stop) and `StopContextCard`, day-split list, resupply legs card (`ResupplyCard.tsx`), `ResupplySelectList.tsx` (the picker's rows), water-carry card, `plan-adapters.ts` (bridges to `@lib` calculators), `plan-inputs-store.ts`, `use-planned-resupply.ts`
  - `routes/` — route builder bar, route geometry, routes store
  - `comments/` — composer, display name, photo upload
  - `import/` — `import-gpx.ts`: document picker → read file → `@lib/gpx-import` (fast-xml-parser adapter) or `@lib/trail-handoff` for `.tracknotes.json` → persist; `elevation-backfill-flow.ts`; `incoming-file.ts` (Android `ACTION_VIEW` / iOS document-type "open with" → stage into cache → `/import` modal; `ACTION_SEND` payloads are not yet read — needs a native `EXTRA_STREAM` reader). Intent filters / document types live in `app.json` and need a new dev build
  - `community/` — share form rules and failure card, report rules, status pill/checks list, My shared routes (`useMySharedRoutes`, `MySharedRoutes.tsx`, `my-shared-routes.ts`)
  - `settings/`, `share/` — display-name, linked-browsers, shared-routes and delete-account sections; check-in sharing
- `api/` — comments API client (device auth, typed fetch wrapper, uuid via `globalThis.expo.uuidv4`)
- `db/` — SQLite layer: `database.ts`, `schema.ts`, and repos (comments, favorites, outbox, routes, imported-trails; `trail-data-repo.deleteTrailScopedRows` is the per-trail cascade)
- `sync/` — comment sync engine, connectivity watcher, sync events. Plans ride the same outbox (`kind` `plan` / `plan-delete`, latest document per plan wins, drained inside the one single-flight drain) and `pullPlans` runs after each trail pull against the `__plans__` `sync_state` row; the server's `updatedAt` is written back so last-writer-wins compares one clock. `sync/plan-sync.ts` is the store→outbox bridge, gated on `isServerKnown`
- `state/` — Zustand stores: settings, downloads, favorites, identity, trail-data (revision/checking/downloading for over-the-air trail data)
- `services/` — trail-loader/assets/bounds (bundled + downloaded + catalog-only + imported: `loadTrail`, `listAllTrails`, `isServerKnown`), trail-catalog/trail-data-updates (over-the-air trail data, above), imported-trail-store (JSON at `Paths.document/trails/{id}.json` + `imported_trails` registry row), local-trail-data (`deleteLocalTrailData`: every piece of local state about a `u_`/`c_` guide that leaves the phone), server-trails (`isServerKnown` — comment sync and the composer are gated off for `u_` ids, so no request ever carries an imported trail id), offline-pack-resolver (an import whose bbox sits inside a bundled trail's coverage borrows that pack; otherwise offline maps are unavailable), tile-service/manager/paths, online-style-service, location-service, position-on-trail, distance-calculator (Naismith ETA)
- `hooks/` — `useLocation` (GPS + trail snapping), `useGuidePosition`
- `navigation/` — header chrome shared by the Expo Router stacks (`HeaderIconButton`, `HeaderActions`). Lives here rather than in a feature slice because both the root and guide headers use it, and slices never import each other. ### Android Emulator (ADB)

An Android emulator (Pixel 7) is available for testing. The user runs Metro dev server (`npx expo start --dev-client`) in a separate terminal. Claude can interact with the emulator via ADB commands.

**Prerequisites**: User must have the emulator running and Metro dev server started before Claude uses these commands.

```bash
adb exec-out screencap -p > /tmp/screenshot.png   # Screenshot (view with Read tool)
# Launch the dev build INTO the JS app (a plain `am start` lands on the Expo Dev Launcher)
adb shell am start -a android.intent.action.VIEW -d "tracknotes://expo-development-client/?url=http%3A%2F%2F10.0.2.2%3A8081" com.tracknotes.app
adb shell am force-stop com.tracknotes.app         # Force stop
adb shell pm clear com.tracknotes.app              # Clear app data (fresh state)
adb shell input tap 540 1200                       # Tap at (x, y)
adb shell input swipe 540 1500 540 500 300         # Swipe (x1 y1 x2 y2 ms)
adb shell input keyevent KEYCODE_BACK              # Back button
adb shell input text "hello"                       # Type text
adb logcat -d -t 50 ReactNativeJS:* *:E | grep -v chatty  # Recent RN logs
adb install -r mobile/android/app/build/outputs/apk/debug/app-debug.apk  # Install APK
```

**Visual verification workflow**: Make changes (Metro hot-reloads) → screenshot → Read the PNG → check `adb logcat` for errors.

### Maestro UI Tests

Maestro test flows live in `mobile/maestro/`. They run locally against the emulator + Metro (no CI job — the Maestro CI workflow was removed 2026-08).

```bash
# Run a single test flow
~/.maestro/bin/maestro test mobile/maestro/app-launch.yaml

# Record a test (writes a flow YAML from manual interaction)
~/.maestro/bin/maestro record mobile/maestro/new-flow.yaml
```

**Flows** (7): `app-launch.yaml` (launch → "My Guides"), `plan-screen.yaml` (guide → Plan → day splits/water carries), `guide-list.yaml`, `view-map.yaml`, `toggle-views.yaml`, `waypoint-detail.yaml`, `add-comment-offline.yaml`. They all start via `shared/launch-dev.yaml`, which deep-links the dev client into Metro — don't run `maestro test mobile/maestro/` on the directory, since that would execute the shared launcher as a standalone flow.
