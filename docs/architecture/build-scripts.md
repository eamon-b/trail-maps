# Build scripts (`scripts/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the everyday commands, the rules and a pointer here; every `npm run` script is in `package.json` and described below; keep this file in step with the code it describes.

- `build-trails.ts` - Generates static trail pages + `public/data/generated/*.json` from GPX/JSON data; the geometry work lives in `@lib/trail-ingest` (`buildTrail`) — this script only supplies the file-system pieces (config, CalTopo GeoJSON, CSV fallback, climate, curated descriptions, waypoint-id registry) and writes the output
- `build-mobile-trails.ts` - Builds mobile-optimized trail JSON (reduced points, truncated precision). A trail with route breaks is simplified one stretch at a time, so Douglas-Peucker cannot drop a break's boundary points and cut the corner across the water; `index` is re-anchored to the result, `displayIndex` is re-anchored the same way, because `displayPoints` is thinned here too: the web copy is no longer a fixed ~3,000 points (see `trail-ingest.ts`'s tolerance ceiling), so the phone clamps it to the same `TARGET_POINTS` budget as `points` — a line no coarser than the array it already ships, and no finer. Every point of both arrays also gets `cumAscent`/`cumDescent`, measured on the full-resolution track *before* thinning (`annotateCumulativeElevation`, skipping the step into each break) and rounded to whole metres: thinning keeps the shape of the line, not its ups and downs, so without them the phone's plans, ETAs and route stats under-counted climb by 14-35%. `processTrail` is exported and `main()` guarded so this is testable. `index.json` records each file's `md5`/`bytes`, and a trail's `updatedAt`/`dataVersion` move only when its md5 changes (the previous index is read back), because `updatedAt` is what the app orders over-the-air copies by
- **Contour zoom tiers** (`tile-pipeline.ts`: `CONTOUR_TIERS`, `contourTierLayer`, `contourTierFilter`, `contourTippecanoeArgs`, `renameContourTiers`) - which elevations appear at which zoom (100 m lines from z9, 50 m from z10, 20 m from z12, 10 m from z13), shared by the world build, the per-trail offline packs and the experiment harness (and by the retired Australia build, below). tippecanoe's `-L {"file","layer"}` object has **no `minzoom` key**: every archive built before 2026-10 passed one and had it silently ignored, so each z9–z12 tile carried every 10 m contour, blew its byte budget, and `--drop-smallest-as-needed` (whose threshold applies to a whole zoom level, set by its densest tile) emptied it — Mt Sonder's live world z9 tile kept one 100 m line — while the Australia archive's `--minimum-detail=4` quantised what survived onto a 16×16 grid: the "jagged when zoomed out" contours. So each tier is read as its own tippecanoe layer (`contour_z9`…), a `-j` feature filter admits it from its minzoom (`$zoom`), and tile-join `-R` folds the layers back into the one served `contour` layer (`renameContourTiers`) — the world build's batch and shard joins do it in passing, the other builds add one tile-join pass. The tippecanoe quality bundle (`CONTOUR_TIPPECANOE_DEFAULTS`: simplification 2 at z9–14, minimum detail 7, 1 MB tiles) is defined once there too; the per-trail packs used to tile with the pre-decision-gate flags. Re-tiering is a tippecanoe-only change: `--merge-only` re-runs, no cell rebuild, wherever the tier files survive. The world build deletes its tiers (`--clean-work`), so for it a re-tier is a full rebuild from the DEM. A world batch's `.done` marker records the tippecanoe release and `contourSettingsHash(WORLD_CONTOUR_OPTIONS)` (the options object the merge itself tiles with) with its cells, so a batch tiled with other settings or by another release is re-tiled, never reused, and `--join-batches` refuses it. tippecanoe is pinned to felt's 2.79.0 (`TIPPECANOE_VERSION`, `bootstrap.sh`'s `TIPPECANOE_REF`): `checkDependencies` refuses any other for the world archive (`TIPPECANOE_ANY_VERSION=1` overrides) and warns for the rest. The Australia archive (`contours/australia.pmtiles`, Geoscience Australia 1" SRTM DEM-S, ~24 h build by the now-deleted `build-contours-australia.ts`) was retired in #228: the same z14 tiles at seven Australian trails were near-identical to the world archive's (elevations within 10–30 m, world 3–15% more line length because DEM-S is hydrologically smoothed, no visible canopy artefacts). It stays in R2 as a frozen public download (last built 2026-10-23, 13.5 GB, CC BY 4.0) and is no longer served or rebuilt
- `build-contours-world.ts` - Builds world contour shards from Copernicus GLO-30 DEM, `--join` converts the shard mbtiles to `.pmtiles` in parallel (tile-join integrity-checks mbtiles inputs on one core, hours at world size, but not pmtiles ones), tile-joins them to world.mbtiles and converts that to a validated world.pmtiles; `--batches-only --batch I,J` tiles only those batches of a shard (0-based), so separate processes can tile one shard's batches in parallel and the shard's own merge reuses them (spec: `plans/world-contour-tiles.md`)
- `fetch-dem-copernicus.ts` - Downloads Copernicus GLO-30 DEM tiles (global, anonymous, per bbox/cells/shard)
- `contour-experiment.ts` - Contour quality experiment harness: settings-matrix builds + side-by-side compare viewer (`npm run experiment:contours`). `baseline` is built from `CONTOUR_TIPPECANOE_DEFAULTS`, so it cannot drift from the builds; `untiered` and `legacy-simp-14` reproduce the archives as deployed before the tier fix, `visvalingam` tries tippecanoe's other simplifier. The compare page draws the real `topo-style.json` contour layers (round joins included), so what you judge is what the app draws
- `lib/world-grid.ts` - Global 2° cell grid, shard partition, Copernicus tile naming
- `lib/trail-data-catalog.ts` - Pure helpers shared by `build-mobile-trails.ts` and `publish-trail-data.ts`: file digests, the `index.json` merge rule (keep `updatedAt` while the md5 is unchanged), the R2 catalog shape, content-addressed keys, validation, and the upload plan
- `lib/xml-adapter-jsdom.ts` - jsdom `XmlAdapter` for `parseGpx` (kept out of `src/lib` so jsdom never enters the mobile bundle)
- `remote/` - Remote-machine world build (runbook: `docs/world-contours-remote-build.md`): bootstrap (`bootstrap.sh` for Ubuntu/Debian, `bootstrap-al2023.sh` for Amazon Linux 2023), `rclone-from-token.sh` (the `[r2]` remote derived from one Cloudflare API token: key id = token id, secret = SHA-256 of the token), the unattended drivers `drive-world.sh` (DEM fetch with retries, a `--cells-only` lane and a pool of shard merges side by side) and `finish-world.sh` (cleanup, `--join`, validation, upload), the single-shard driver `run-shard.sh`, `status.sh`, `upload-world.sh`
- `sync-te-araroa.ts` - `npm run sync:te-araroa`: copies the published Te Araroa route out of the `te-araroa-data` package into `data/trails/te_araroa/` (never hand-edit it; fix it upstream)
- `build-region-shapes.ts` - `npm run build:region-shapes`: regenerates `src/lib/region-shapes.ts` (coarse Natural Earth outlines for `@lib/region-detect`) from the regions in `src/lib/trail-regions.ts`
- `fetch-climate.ts` - Fetches historical climate data for trail locations
- `fetch-elevation.ts` - Fetches elevation data
- `fetch-pois.ts` - Fetches OSM POIs along each trail corridor (`npm run fetch:pois [trail-id]`) through `@lib/osm-poi`, `@lib/overpass-client` and `@lib/poi-enrichment` — the `src/lib` port of the `gpx-tools` search, which the phone runs too, held to that library byte for byte by `scripts/osm-poi-parity.test.ts`. Reads track geometry from `public/data/generated/{id}.json` (so `build:trails` must have run) and writes the results to `data/trails/<dir>/pois.json` — in the repo, where a rebuild cannot wipe them. `--endpoint <url>` / `OVERPASS_ENDPOINT` and `--timeout <seconds>` pick the Overpass instance; mirrors come and go, so try them in turn: `overpass.private.coffee` served the Australian trails (2026-09-08, `--timeout 120`), but by 2026-09-30 it timed out from a cloud session, where `overpass-api.de` reset the connection and `overpass.kumi.systems` timed out too. What answered there was `--endpoint https://maps.mail.ru/osm/tools/overpass/api/interpreter`, which drops any query past about 60 s, so it wants small cheap ones: `--max-vertices 60 --timeout 55` (or 150/120 for a lighter trail). A run that loses chunks merges what succeeded into the existing file instead of replacing it (so a whole-trail run can never ship a hole), prints which chunks failed and exits 1 — re-run it until no chunk fails (how the CDT's file was built); `--force-replace` writes the partial result as-is. A POI's km is measured against the track as fetched, so a later track edit (or placement fix) leaves it stale; `--reposition` re-places the POIs already in `pois.json` on the current track with no Overpass query (exactly a fetch's placement, so an unchanged trail comes out byte-identical; with `--dry-run` it only reports what would move or drop, and writes nothing), and `build-trails` fails when any stored km or category differs from that placement (`misplacedPois`, about 12 s across all trails) — it writes the trail's generated JSON first, so `--reposition` (which reads the track from it) sees the edited track; any windowed fetch (merged, or the first file for a trail with no `pois.json` yet) and any partial fetch's merge are re-placed on the whole route for the same reason (`placesOnWholeRoute`) — the AAWT's Blue Waterholes POIs sat at km 790 of 688 and the SOBO view listed them at km 0. On 2026-10-06 `overpass.private.coffee` answered again (`--timeout 120`, Shikoku in one 182 s query), but its data lagged: the same day `maps.mail.ru` (`--max-vertices 60 --timeout 55`) returned a 2026-09-21 survey of central Tokushima that it lacked
- `fetch-access.ts` - Finds where each off-route waypoint is walked to from (`npm run fetch:access <trail-id>`): every main-route waypoint at least `--min-distance` (150 m) off the line — not turn-offs, not ones within 200 m of one of the trail's side trips (the side trip is the way there, and OSM may lack it), and not ones whose source already gives `offTrailKm` (and, with the same exclusions, every waypoint the main route did not match — an off-trail row or an alternate's own — that is off an **alternate** by `--min-distance` up to the trail's match radius, `waypointMaxDistance`, 500 m by default, and nearer it than the main route) — is routed over OSM's walkable ways (`isWalkableWay`: no motorways, nothing `foot=no`/`access=private`) with `@lib/access-routing`, heights from Copernicus GLO-30 read by HTTP range requests (`scripts/lib/dem-sampler.ts`, the `geotiff` devDependency; behind a proxy run with `NODE_USE_ENV_PROXY=1`). Only a tile the bucket answers 404 for is open ocean; any other failure to read heights fails that query like an Overpass error (retried, previous entry kept, exit 1), never a flat walk. Nearby places share one Overpass query (boxes ≤ 10 km across: bigger ones over Japanese cities drew HTTP 500s), and every answer is cached in the gitignored `data/osm-ways-cache/`, so a change to the routing re-runs from disk (`--refresh` re-downloads; a box cached longer than `--max-cache-age`, 90 days, is fetched again). A 429 (or a 503 with `Retry-After`) waits as long as the mirror asks, up to 5 minutes, before the next query. Failed queries get three more passes a minute apart; `--only <ids>` re-runs what a run lost. A waypoint the build merged near-duplicates into (`dedupeWaypoints`, its `mergedIds`) gives every twin the same entry, or the merge would keep the twin without one on the next build; on such a trail a second fetch-and-build round can still move a survivor, so re-run until `fetch-access` changes nothing. A place off an alternate is routed to that alternate's line (`alternateRoute`: km from its `points[0]`, the branch point) and its entry names the alternate as `variant`, with `junctionKm`/`nearestKm` along it; an alternate whose name another shares is never routed to, since the entry names it. Writes `data/trails/<dir>/access.json` and prints each place's km before → after; a failed query keeps the place's previous entry and exits 1, so re-run until it exits 0. Same mirror caveats as `fetch-pois.ts`: on 2026-10-11 `overpass.private.coffee` 500'd most queries and `maps.mail.ru` (`--timeout 55`) served them
- `fetch-font-glyphs.ts` - Fetches font glyphs for map label rendering
- `build-tiles.ts` - Builds map tiles for offline use: a Protomaps vector base map plus contour lines from the Copernicus GLO-30 DEM — everywhere, Australia included, so a pack draws the same lines as the online `world` source (Australian packs were cut from SRTM until #228). Fetch the DEM first with `fetch-dem-copernicus.ts --bbox …`; a build with tiles missing fails and prints the exact command. Composited by a custom MapLibre style. Ready-made providers were rejected (Feb 2026): OpenFreeMap/Protomaps have no contours, OpenTopoMap is raster-only, MapTiler On-Prem and Thunderforest's offline tier are too expensive for a non-commercial project, and Mapbox Outdoors would mean leaving MapLibre. Hillshade was prototyped and dropped: little gain on a phone screen, nearly double the pack size (~60 MB more for Bibbulmun) and Android raster compositing bugs
- `e2e-tile-check.mjs` - Probes the deployed tile infrastructure through the URLs the app uses (`mobile/eas.json`): contour worker health and tiles, and an offline pack for **every trail in `mobile/assets/trails/index.json`** (manifest lists `base.mbtiles` and `contours.mbtiles`, each object present at the manifest size). `npm run check:tile-packs` runs the pack and tier checks; the `tile-packs` workflow runs it when the bundled trail list changes and weekly, so a new trail fails CI until its pack is built (`build:tiles --trail <id>`) and uploaded (`upload:tiles <id>`). `--tiered` (`npm run check:tiered`, and every full run) checks the contour tiers are live: the worker's Mt Sonder z9 tile (`world` and `contours`, 9/444/290) holds only 100 m lines at ~1,500 features, and every z9 tile of every pack's `contours.mbtiles` holds only 100 m lines, with at least one contour feature per pack (a pack whose tiers were never folded into `contour` draws nothing). `--alias` (`npm run check:contours-alias`, and every full run; not part of `--tiered`, because the `tile-packs` workflow runs that on pull requests, before a worker change is deployed) checks that `contours` really is the alias of `world` (#228), which the density check cannot tell, since the retired Australia archive was tiered too: `/health`'s `sources.contours.archive.key` must be `contours/world.pmtiles` (the alias deploy is live), and `/contours/…` and `/world/…` must serve byte-identical tiles through the edge for Mt Sonder z9 and a Kosciuszko z12 (the purge of the edge-cached `/contours/*` URLs took effect). The pack z9 tiles are read four packs at a time with HTTP Range requests through `scripts/lib/http-mbtiles.mjs`, a read-only SQLite walker for every mbtiles layout (plain `tiles`; `map`/`images` with `images` keyed by `tile_id` as tippecanoe writes it or by `(zoom_level, tile_id)` as tile-join does, which every tiered pack is) that waits out the data domain's 429s and retries a 200 for up to 75 s (the edge now and then ignores the Range on the packs too big for its cache, CDT and Te Araroa — the tile-packs failure of 2026-10-30), closing each such body unread, and decoded by `scripts/lib/mvt-contours.mjs`, both Node built-ins only. It passed on 2026-10-24 once the #135 rebuild was live, so `check:tile-packs` (and with it the weekly workflow) now includes it
- `upload-tiles.sh` - `npm run upload:tiles [id...]`: publishes built packs to R2, manifest last. A manifest file absent locally is skipped when the bucket already serves its content-addressed key at the manifest's size, so a pack that changed one file can be republished without downloading the rest. Every published manifest is then purged from Cloudflare's edge (`CLOUDFLARE_API_TOKEN` with Cache Purge on the zone): the edge has served `manifest.json` days past its `max-age`, and the app fetches the plain URL, so an unpurged republish reaches no phone. No `CLOUDFLARE_API_TOKEN` refuses the whole run before anything is uploaded (`require_purge_token`); a purge that fails anyway fails the script after the upload; `--no-purge` opts out when purging by hand. The app fetches the manifest with a per-minute `?m=` (`tile-service.ts` `manifestUrl`, like the trail catalog), so the purge is a backup for current builds and still the only path for older ones
- `cleanup-superseded-tiles.ts` - `npm run cleanup:tiles`: the pack objects at old content-addressed keys that `upload-tiles.sh` leaves behind. Lists the bucket with rclone (`RCLONE_REMOTE`; wrangler cannot list), reads each pack prefix's live `manifest.json` from the bucket, and plans to delete every `.mbtiles` directly under the prefix that the manifest references neither by `key` nor by plain `name` (pre-content-addressing app builds, and a current build that cannot read the manifest, download the plain name). The grace (`--grace-days`, 7) runs from when the object was superseded: a prefix whose manifest is younger than it is skipped, and an object younger than it (an upload in progress) is kept. Never touches a prefix whose manifest it cannot read, sub-directories, other files or other prefixes. Dry run by default, `--delete` deletes; `--world-build` does the same over `contours/world-build/`, refusing unless `contours/world.pmtiles` is newer than everything under it
- `download-dem.sh`, `download-dem-australia.sh` - Download SRTM 1-arc-second DEM tiles from NASA EarthData (an EarthData account is required), per trail or for all of Australia, into `data/dem/` (the SRTM cache `tile-pipeline.ts` reads as `DEM_CACHE_DIR`). Since #228 the online `world` archive and the offline packs' contours come from Copernicus GLO-30 instead, but `build-grid-tiles.ts` still cuts its grid packs' contours from this SRTM cache
- `build-grid-tiles.ts` - Builds grid-based map tiles; `upload-grid-resume.sh` resumes their R2 upload, retrying failed objects instead of aborting (how-to: `scripts/grid-tiles-howto.txt`). Nothing in the app or site reads the `grid/` packs yet
- `tile-pipeline.ts` - Orchestrates the full tile generation pipeline
- `process-heysen-waypoints.ts` - Trail-specific waypoint data processing
- `process-shikoku-caltopo.ts` - Builds `data/trails/shikoku/shikoku-t1-t23.gpx` (Shikoku Henro, Temples 1-23) from a CalTopo GeoJSON export of the whole island: keeps the purple "88 Temple Pilgrimage" line and every marker within 3 km, types each by its folder, and adds Temples 3-9 and the Shosanji Okunoin from OpenStreetMap. The export itself is not committed — a GeoJSON in the trail directory would be read as a category source keyed by folder names the classifier does not know. The Okunoin out-and-back is lifted off the route by `extractSpurs`, and `waypointMaxDistance` is 3000 m so pilgrim lodgings a short walk off the line stay on the datasheet and plan page. Places the map lacks (Sudachi-an and the other Temple 11-13 lodgings), closures and corrected descriptions are curated in the script itself (`CURATED_WAYPOINTS`, `CLOSED_MARKERS`, `DESCRIPTION_OVERRIDES`) and applied on every run; `--reapply` applies them to the committed GPX when there is no fresh export (the GPX round-trips through `parseGpx`/`generateGpx` byte for byte, so the track is untouched). The map has only the one line, so alternates live in `scripts/data/` (today `shikoku-kamiyama-alternate.json`: Nabeiwa → Kamiyama → Kamiyama Onsen → the Akui river, routed over OSM roads with Copernicus GLO-30 elevation) and are written after the main track as `Alternative: …` `<trk>`s on every run, `--reapply` included. henroyado.com's Tokushima inn list is applied the same way from `scripts/data/shikoku-henroyado-inns.json`: `inns` are added as waypoints, each recording where its position came from (henroyado.com publishes none — OSM, henro.org, the inn's own map, GSI address search, Rakuten Travel's map, or the Street View point on min88.jp's inn page; min88's map *centres* sit a zoom-dependent ~3 km west of the pin, so never use those), `listed` appends a `henroyado.com (Oct 2026): …` line to markers the map already has (replaced, not stacked, on a re-run), and `omitted` records the inns left out and why
- `process-three-passes.ts` - Builds `data/trails/three_passes/three-passes.gpx` (Everest Three Passes from Jiri) from the output of the Nepal generator in `~/projects/GPX/nepal` (Python, not version controlled; it routes each leg over the OSM footpath network with SRTM elevation). Reads `three-passes-from-jiri.gpx` and `three-passes-quiet-variants.gpx`, joins the day tracks into one main track (the Day 9 Namche acclimatisation loop becomes a side trip), builds the three alternatives from one or more generator legs, keeps or renames the side trips, and types every waypoint (`Village` → `teahouse`, `Pass` → `gap`, Jiri/Namche/Lukla → `town`). It fails on a gap of more than 50 m at a join, an unknown side trip or an untyped waypoint. The generator's per-track notes are not carried (the GPX parser drops `<trk><desc>`). `npx tsx scripts/process-three-passes.ts [nepal-dir] [output.gpx]`, then rebuild.
- `publish-trail-data.ts` - Over-the-air trail data (`npm run publish:trail-data`; runbook: `docs/trail-data-updates.md`). Checks `mobile/assets/trails/index.json` matches its files byte for byte, then uploads each file to R2 at content-addressed `trails/v1/<id>.<md5[0..12]>.json` (only keys the live catalog lacks) and `trails/v1/catalog.json` **last**. `--dry-run` prints the plan, `--check` exits 1 when the live catalog differs, `--all` re-uploads everything. Two guards against a publish from a stale checkout: it refuses to roll a trail's live `updatedAt` back, and the catalog records the `sourceCommit` it was published from, so a checkout whose HEAD does not descend from it is refused too (`--force` overrides both; without git it warns and continues). Dropping a trail the live catalog has is refused unless that id is named with `--remove <id>` (or `--force`), because a trail missing from `index.json` is usually a build that failed for it, not a decision. `v1` is the trail JSON format: a breaking shape change publishes under `v2` and leaves v1 frozen for old app builds
- `upload-descriptions.ts` - PUTs curated waypoint descriptions to the comments API (`npm run upload:descriptions`, admin token in `$TRACKNOTES_ADMIN_TOKEN`; `--dry-run` prints the requests)
- `measure-community-poi-cpu.ts` - `npx tsx scripts/measure-community-poi-cpu.ts [trail-id...]` (after `build:trails`): times each CPU step of the comments API's community-route POI enrichment on bundled trails standing in for community routes, with their real POIs and a synthetic answer at the enrichment's cap — the numbers to weigh against the Workers plan's CPU limit (`workers.md`, "community route POIs"). Makes no request
