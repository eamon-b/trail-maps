# Core library (`src/lib/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

Shared processing modules (used by both web and mobile):
- `distance.ts` - Haversine distance calculations
- `gpx-parser.ts` - Parse GPX XML into structured data; `parseGpx(xml, adapter?, limits?)` is platform-neutral (see XML adapters below) and parses coordinates strictly (throws instead of plotting 0,0)
- `xml-adapter.ts` - Minimal XML node interface (`querySelectorAll`/`querySelector`/`childElement`/`getAttribute`/`textContent`, tag selectors only) + the DOMParser adapter. `querySelector` searches every descendant, so a field that must be the element's *own* (`<wpt>`'s `<name>`/`<type>`, not its `<link>`'s) goes through `childElement`
- `xml-adapter-fxp.ts` - fast-xml-parser adapter (the React Native path — Hermes has no DOMParser)
- `parse-coordinate.ts` - Whole-string decimal parsing for coordinates (`parseFloat` alone accepts `-37.1abc` and `Infinity`)
- `track-spurs.ts` - Detects and extracts self-retraces ("spurs") folded into the main-route segment, e.g. the Larapinta's Mt Sonder summit return, which name-based classification cannot see
- `waypoint-dedupe.ts` - Merges near-duplicate waypoints (same cleaned name and type a few tens of metres apart) in built trail data
- `trail-reverse.ts`, `variant-reverse.ts` - Direction reversal for a whole trail and for its variants (alternates, side trips), shared by web and mobile
- `plan-direction.ts` - The only sanctioned conversion between stored NOBO-absolute plan km and the active direction's km
- `format-distance.ts` - Unit-aware distance formatting, the single choke point for km → display string
- `climate-aggregate.ts` - Aggregates Open-Meteo daily series into monthly averages (shared by `fetch-climate.ts` and the app for imported trails)
- `escape.ts` - `escapeHtml` (see the hard rule in `CLAUDE.md`)
- `comments-api-types.ts` - Wire types for the comments API, imported by the app and the worker. Plain types only: no runtime imports, no DOM or Node globals
- `gpx-optimizer.ts` - Track simplification (Douglas-Peucker), elevation spike removal/smoothing, elevation stats
- `track-simplify.ts` - Target-point-count simplification + coordinate truncation (the mobile point budget)
- `track-classification.ts` - Classify main/alternate/side-trip/**terminus** tracks. A `terminus` (`terminusPatterns`, default `['^Terminus:', '\\bTerminus\\b']`, collected into `terminusTracks`) is an *alternative trail end*: it branches off the main line at one end and its other end is deliberately free, 10-31 km off the route (the CDT's Chief Mountain, Columbus and Antelope Wells). It is matched **after** alternate and side trip, so a track a trail already names `Alternate: …` keeps that class. Several main tracks are normally chained by `combineTracksGeographically`, which orders them by proximity and bridges every join. A trail whose `trackClassification.stretches` is set instead uses `concatenateStretches`, which keeps the file's order and records any join wider than `minGapMeters` as a **route break** — somewhere the walking route genuinely stops and resumes (a ferry, an unbridged river). Opt-in per trail: turning it on for a file whose tracks are not in walking order would silently reorder the route
- `route-breaks.ts` - Reading those breaks back out for anything that draws the route (`splitAtRouteBreaks`, `routeBreakCrossings`). Breaks leave `track.points` a single flat array — every other consumer wants one ladder of cumulative distance — so only line-drawing code needs this. Used by both maps: the web viewer's `drawMainRoute` and mobile's `buildTrailLine` (a MultiLineString, one stretch per line). Anything that draws or climbs *part* of the route uses the other two: `sliceAcrossRouteBreaks` (the plan page's day lines, mobile custom-route spans) and `routeBreakStarts`, the index set the elevation helpers take so a ferry's landing-to-landing height difference is never climbed
- `waypoint-classifier.ts` - Classify waypoint types (town, hut, water, etc.). Five tiers: CalTopo folder → `KNOWN_TOWNS` → name prefix (`C:`/`WT:`…, delimiter required) → `KEYWORD_RULES` word matching → `waypoint`. The keyword tier is opt-in (`inferFromKeywords`) and is **on for user imports, off for the curated build** — guessing types for curated trails would churn `public/data/generated/*.json` for no gain
- `map-glyphs.ts` / `waypoint-glyphs.ts` - The one map icon set for both platforms. `map-glyphs.ts` holds the shapes (`MAP_GLYPHS`: 96x96 SVG bodies inked with `currentColor`; no imports and erasable TypeScript only, because `mobile/scripts/build-map-icons.mjs` loads it straight through Node's type stripping to rasterise `mobile/assets/map-icons/*.png`). `waypoint-glyphs.ts` maps a waypoint type (`waypointGlyph`, turn-offs via `baseWaypointType`) or OSM POI category (`poiGlyph`) to a glyph, and the glyph to one of six colour families (`waypointFamily`/`poiFamily`: water, camp, town, shelter, hazard, neutral). The family is derived from the glyph, never listed per type, so an alias cannot get the water drop on a grey ring. Mobile resolves a family to its `waypoint*` theme tokens (`elevation/waypoint-category.ts`, which also drives the list filter chips); the web inlines `glyphSvg` (`src/web/trails/waypoint-icons.ts`) and colours it with the `--wp-*` custom properties in `styles.css`. No emoji anywhere a waypoint type is drawn
- `waypoint-taxonomy.ts` - The waypoint type vocabulary (`WAYPOINT_TYPES`, `WAYPOINT_TYPE_LABELS`, `waypointTypeLabel`) and the water/resupply family predicates (`isWaterWaypoint`, `isResupplyWaypoint`, `matchesWaypointFamily`). These predicates are the single home of rules that used to be duplicated across `water-carry-calculator`, `day-calculator` and `resupply-calculator`; they also accept the type aliases real-world GPX uses (`spring`, `supermarket`, …), which our own classifier never emits. `teahouse` (a lodge on a teahouse trek: bed, meals and water) is the one type in both families and is an overnight type (`plan-editor` `OVERNIGHT_TYPES`); its turn-off `teahouse-access` is resupply but never water. It has its own glyph (a steaming cup, shelter family), is a dedup match for OSM `camping` and `restaurant` POIs, and the phone's next-of-type strip counts it as the next shelter, town and water at once
- `trail-types.ts` - Shared `ProcessedTrail` / `TrackData` / `EnrichedWaypoint` / `RouteVariant` / `TrailConfig` — the shape of `public/data/generated/{id}.json`. `RouteVariant.type` is `'alternate' | 'side-trip' | 'terminus'`; **termini live in `sideTrips`**, not in an array of their own — every consumer of that list already means "routes that leave the trail and do not come back", so one array keeps the map lines, camera bounds, datasheet, reversal, mobile slimmer and handoff parser working unchanged, and anything that must tell them apart reads `type === 'terminus'`. A terminus has exactly one junction (`startDistance`, at `points[0]`) and never an `endDistance`
- `trail-ingest.ts` - `buildTrail(gpx, options)`: the whole GPX → `ProcessedTrail` pipeline (route selection, cumulative distance, display simplification, waypoint enrichment, variant junctions, off-trail split), with hooks for the build script's file-system/registry concerns. `track.displayPoints` aims at `DEFAULT_TARGET_DISPLAY_POINTS` (3,000) but `calculateAdaptiveTolerance` is capped at `MAX_TOLERANCE_METERS` (25 m), so a long trail overshoots that target rather than losing the shape of its line — the CDT keeps ~21,000 display points instead of drawing as straight chords beside its full-resolution alternates. A route break adds neither distance nor climb, is simplified around rather than across, and is published as `track.breaks`. **Waypoint km must stay on the track's own scale**: `enrichWaypoints`/`calculateSegmentStats` take the break indices and skip the same legs, or waypoints drift past the end of the trail they are measured along. **Variants read forwards**: `findVariantJunctions`/`attachVariantsToParents` turn a variant round (points reversed, ascent/descent swapped) when its source track was drawn against the trail, so `points[0]` is always the branch point at `startDistance`. Variant waypoint km and a child alternate's km along its parent both count from `points[0]`, so never swap the junction pair without reversing the points. **Off-route places**: a waypoint is attached to the route point nearest it in a straight line, unless `options.waypointAccess` (the build's `data/trails/<dir>/access.json`, by waypoint id) gives a junction found over OSM — then it is attached there, keeps its own position, and gets the walk in as `offTrailKm`, `offTrailAscentM`/`offTrailDescentM` (climb walking in), `accessMode: 'foot'` and, for an `osm` entry, the way itself as `offTrailPath` (`[lat, lon]` junction → place, only ever drawn: the web viewer and plan page dot it while the place's popup is open — the plan page also for as long as the place is a stop — through `src/web/trails/access-path.ts`; the phone's map after a marker tap or a "Show on map" from the waypoint screen or a Today, Day or Stops row (`features/guide/ShowOnMap.tsx`). GPX imports and community copies never carry it: GPX has no `tn:` field for it, and `community-checks` drops it — `docs/gpx-import.md` says so; a `.tracknotes.json` handoff keeps it, `trail-handoff`'s `readAccessPath`) (`matchAtJunctions`/`restoreJunctionPositions`). Its km is the junction's on the route *line* (`placeAtJunctionKm`), not at the nearest vertex — on a road walk vertices can be 800 m apart — and its vertex (`trackIndex`, elevation, running climb) is the nearer end of that segment, so neither steps backwards down the list. On a loop a junction-placed place goes to whichever end is nearer (Great South West Walk's Portland, walked to from km 253.5 of 253.7); every other waypoint in range of both ends stays at km 0. A `none` entry (no way found), or one the build ignored, is walked as the straight line to the route (`waypointAccessUnrouted` → `offTrailKm`, no `accessMode`). An entry is ignored, with a warning, when the place is beyond the match radius *and* further from its junction in a straight line than its walk in (+50 m) — the place moved, and a stale entry must never pull an off-trail place onto the route — or its junction is over 100 m from the route line (re-run `fetch-access`); an entry whose walk does reach the place applies however far off the route it is, so a long walk-in never needs a trail-wide `waypointMaxDistance`; `scripts/access-data.test.ts` fails CI when a committed entry names a retired id or the bundled trail does not put a routed place at its junction km. **Places off an alternate**: an entry with a `variant` (the alternate's name) never touches the main route; `options.variantWaypointAccess` hands it to `enrichVariantWaypoints`, which runs the same passes (`matchAtJunctions` → `placeAtJunctionKm` → `restoreJunctionPositions` → `straightLineAccess`, generic over the main route's and an alternate's rows) on that alternate's own line with the variant match radius (200 m), so the place joins the alternate's `waypoints` at its junction's km along it (`startDistance` + km from `points[0]`) with the walk in — Shikoku's Cotton Field Campground, 560 m off the Kamiyama alternative and 3 km from the main route, which before had no row on the alternate at all. Only alternates take entries (a side trip is the way to what is near it; a terminus ends the trail); an alternate with none is enriched exactly as before, and an entry naming an alternate the trail lacks is warned about and ignored. The place's off-trail row (it is still beyond the main route's radius) stays, as every alternate's waypoints always have
- `gpx-import.ts` - `importGpx(xmlText, options)`: runtime import for user-supplied GPX (elevation cleaning on, `u_`/`uw_` synthetic ids, `ImportReport`). The user-facing spec of the pipeline is `docs/gpx-import.md` — keep it in step with behaviour changes here and in `trail-ingest.ts`. It is rendered into the site as `how-import-works.html` at build time (the `gpx-import-doc` plugin in `vite.config.ts`)
- `elevation-backfill.ts` - Open-Elevation backfill for GPX without `<ele>` (`backfillElevation` batches of 100, ≤2000 samples interpolated by distance; `applyElevation` re-derives ascent/waypoint stats via `recomputeTrailElevation`); `trailHasElevation`/`trailElevationIsUsable` drive the "distance-only estimate" labels
- `comment-targets.ts` - The ids a comment may be filed under, by form (`commentTargetKind`): `w_` curated registry ids, `uw_` a community route's own waypoint ids (what the import minted, `_<n>` suffix allowed), `hw_` shared hiker waypoints, `osm_…` POIs; `commentTargetFitsTrail` keeps `w_` to curated trails and `uw_` to `c_` routes. The comments API's `validateCommentTarget` and the phone's `CommentsSection` both use it, so the composer is offered only where the server takes the comment
- `contribution-licence.ts` - The licence line under everything a hiker makes public (CC0 + the terms of service, `contributionLicenceLine`) and the published `TERMS_URL`/`PRIVACY_POLICY_URL` (`public/terms.html`, `public/privacy.html`, drafted from `docs/terms-of-service.md` / `docs/privacy-policy.md`). `contributionPrivacyLine` is the second line beside it, linking the privacy policy (the notice at collection). Both show under every form that publishes something: the phone's comment composer, waypoint form ("Everyone") and route-share form (`ContributionLicence.tsx`), and the web's route-share and route Edit forms (`renderContributionLicence` in `src/web/community-ui.ts`).
- `community-types.ts` - Wire contract for **community routes** (spec: `plans/community-routes.md`): `c_` ids (`isCommunityRouteId`), statuses `unverified`/`verified`/`hidden`/`removed`, `CommunityRouteSummary`/`CommunityRouteDetail` (`hiddenReason` for the owner/admin of a hidden route; `statusNote` admin-only), the AI review shape, report reasons, `COMMUNITY_LIMITS`
- `user-waypoints.ts` - **Hiker waypoints**: places a hiker adds to a trail on the phone, `private` (SQLite only, never sent) or `shared` (the comments API, pulled by every phone on that trail — the missing water source or shop). One shape (`UserWaypoint`), `hw_<uuid>` ids (`isUserWaypointId`; the comments API takes comments on a shared one, and only while the server holds it on that trail), the offered types (`USER_WAYPOINT_TYPES`, a subset of `WAYPOINT_TYPES` the calculators already understand), `USER_WAYPOINT_LIMITS`, and `checkUserWaypointInput`, run by the form and again by the worker. `placeUserWaypoints` merges them into a trail *as stored* (before direction): each lands at the km of the nearest point on the main route (`placeOnTrack`, which is `position-on-trail`'s `snapToTrail` — the GPS snap — so a waypoint and a fix at one spot read the same km), the curated waypoint after it gets its arriving leg re-measured, one further than `onRouteMetres` (500 m, `buildTrail`'s match radius) of a water/campsite/hut/resupply/food/accommodation/town type is placed as a turn-off (`<type>-access` with the straight-line `offTrailKm`) so the water and resupply calculators never count a place down a side valley as on the route, and it carries a `userWaypoint` field (`userWaypointInfo`) that marks it apart. Another hiker's shared pin (`isOtherHikersWaypoint`: not `mine`) counts like any other place — its water shortens a carry — and the phone's list and waypoint screen say who reported it and when ("Reported by Jo · 12 Oct", `hikerReportLine` in `features/guide/waypoint-detail.ts`), so the hiker judges it; no hedging or advice is added to that line. They never enter the build, `data/waypoint-ids.json` or `public/data/generated/*.json`
- `region-detect.ts` / `region-shapes.ts` - Which country and states a route is in, offline: `detectRegion(points)` samples 256 points against Natural Earth outlines of every country and state in `trail-regions.ts`, plus the unlisted countries bordering them (`other`: a route in Lesotho or Andorra is LS or AD, never pulled into its neighbour). `region-shapes.ts` is generated by `npm run build:region-shapes`: land borders are simplified once for both neighbours (~500 m, so a point near one is in exactly one shape), coastlines to ~5-10 km (a point just off one takes the nearest shape within 30 km), small islands kept outside the Arctic. It returns the majority country, the states in route order (each holding ≥ 2 % of the samples), the majority `state`, and `seen` — every country and state any sample is in. It prefills the region on both community share forms (the hiker can change it; the phone only prefills a listed country), and `checkCommunityRegion` in `community-checks.ts` is the worker's `region` check, which warns only when the chosen country or state holds none of the samples — the hiker's choice is always stored as given. Every bundled trail detects as its `trail.json` `country`/`states` (`region-detect.test.ts`)
- `community-checks.ts` - `runCommunityChecks(trail, {name, description, gpxText?})`: the automatic checks for a shared community route — shape, length, points, distance-consistency, speed, elevation, gaps, metadata, waypoints. Run by the clients before upload and again by the worker, whose result counts. It never trusts its input. Coordinates, elevations, names, text and waypoint `trackIndex` are validated and kept; a `trackIndex` whose point is beyond `buildTrail`'s match radius of the waypoint (500 m route, 200 m variant) is re-placed as an import would place it (nearest point in range, else off-trail). Everything derived is rebuilt from that geometry the way `buildTrail` builds an import: point `dist`, length, `displayPoints` (Douglas-Peucker, budgeted, stride fallback), climb (3 m hysteresis), waypoint km/legs/climb, off-trail `distanceFromTrail`, and variant length, climb, junctions and `parent`. A variant must start within 500 m of the route or an attached alternate. Route breaks, POIs, `cumAscent`/`cumDescent`, timestamps, climate and the client's direction labels are dropped. The client's own km survive only for `distance-consistency`. The result is returned as `trail`, with `stats` for the row (`waypointCount` counts main, off-trail and variant waypoints). `speed` reads the raw GPX through `gpxMovingSpeedKmh` (a string scan, null under 10 timed points) and passes with a note when there is none. O(n log n) on real tracks; messages are plain English for the person sharing. OSM POI density is deliberately not a check — it varies by trail
- `trail-regions.ts` - Countries (ISO alpha-2) and their state/region codes, `LENGTH_BANDS`, and `matchesFilter`/`sortTrails`/`groupTrails` (Country → State, first state wins, "Other" last). Shared by the web landing page, the app's My Guides and the community forms. `trail.json` carries `country`, `states` (route order) and an optional `featured`; `scripts/trail-regions-data.test.ts` enforces them. The web and mobile `index.json` and the R2 trail catalog carry them, the per-trail mobile JSON does not (`stripListOnlyConfig`), so a list-only edit never moves a trail's md5 or triggers an over-the-air download
- `trail-handoff.ts` - `<slug>.tracknotes.json` web → mobile handoff format (`wrapTrailForHandoff`, strict `parseHandoffJson`)
- `poi-display.ts` - The platform-neutral half of showing OSM POIs, shared by the web viewer and the app: category labels, `poiDisplayName`, `summarisePoiTags` (+ the `safeHttpUrl`/`safeTelUrl` guards every POI link must pass), `slimPoi` (what `build-mobile-trails.ts` and the mobile import store write), the `PoiFilterState` shape and its normaliser, `visiblePois`/`countPoisByCategory` (both skip `duplicateOf`), `duplicatePoisFor` (the POIs flagged `duplicateOf` a waypoint id: the phone's waypoint screen and the web's waypoint popups show their tags as "From OpenStreetMap"), `poisBetween` (a km span, sorted), `interleavePoisByDistance`, `mirrorPoiDistances`, `poiVariantFinder` (for a trail's variants, the alternate or side trip a POI was found along, else null), the slash-free `poiRouteKey` (`type-id`) that names a POI in an Expo Router param, `poiCommentId` (`osm_<type>_<id>`, the id a POI's comments are filed under in the comments API, apart from `w_`/`hw_`) and `poiNoteUrl` (OSM's new-note page with its marker on the POI). `src/web/trails/trail-pois-ui.ts` re-exports it and keeps only the HTML/`localStorage` half
- `elevation-axis.ts` - `eleBounds`: an elevation profile's default y-axis, 0 m (or a below-sea-level low point) to just above the track's high point, never fitted to its low point. Shared by the phone's elevation pane (`features/elevation/geometry.ts` re-exports it) and both web profiles (trail page, plan page), so the same climb looks the same on each. `eleAxis` is the web's drawn axis over those bounds: nice tick steps, the top raised to the next line so the high point is never above the last label
- `text-links.ts` - `splitTextLinks`: free text → plain/link segments (`kind` `url`/`email`/`phone`). URLs go through `safeHttpUrl` (http(s) only), emails become `mailto:`, phone numbers `tel:` through `safeTelUrl`. A phone number needs 8-15 digits and a separator, a leading `+` or a `Tel:`/`Phone:` label, so OSM ids, coordinates, dates and `0800-1700` ranges in descriptions stay plain. Waypoint descriptions carry bare URLs (Shikoku's henro.org pages), inn emails and phone numbers; the web viewer renders them through `linkifyText` (`src/web/linkify-text.ts`, kept out of `web-utils` so the landing page does not load `poi-display`) and the app's waypoint detail screen with `mobile/src/features/guide/LinkifiedText.tsx`, which is selectable (long-press to copy) and opens a tapped link in the browser, mail app or dialler
- `access-routing.ts` - Where an off-route place is walked to from: `buildWalkNetwork` (OSM ways → graph joined at shared nodes, split into ≤ 25 m edges) and `findAccess`, a shortest-path search from the place (the ways within 60 m of the nearest one, reached cross-country at 1.5× cost; only if none of those leads to the route, any way within 300 m — without that, a road the route follows 200 m away across a river beat the place's own lane; and never straight to the route itself from more than 150 m — 500 m over ground no steeper than 1 in 5 — which drew Rainbow Falls 225 m down a cliff) to the first node within 35 m of the route line, never across a route break. The cost is the *round trip* by Naismith's rule (a metre of climb = 8.3 m of flat): with one junction the route is walked whole either way, so the round trip is all that differs between junctions, and it climbs every height difference along the path once, which makes edges symmetric. Shikoku's Maekawa Campground is why: 1.4 km from the top of the Temple 20 climb in a straight line, 2.8 km of flat road from the bottom. Returns the junction and its km, the walk's length, climb in (3 m hysteresis), cross-country part and path. Pure; the caller supplies ways and heights (`scripts/fetch-access.ts`)
- `poi-noise.ts` / `poi-dedup.ts` / `poi-urban.ts` - The build/import-time passes between a raw `pois.json` and the shipped `pois` array: drop category-wide noise, flag POIs that duplicate a curated waypoint, thin city stretches (see `pois.json` under Trail Data). `markDuplicatePois` skips a waypoint on latitude alone before tokenising its name — exact, and what keeps POIs × waypoints cheap on a long route
- `osm-poi.ts` / `overpass-client.ts` / `poi-enrichment.ts` - The OpenStreetMap search itself, ported from `gpx-tools` so the phone can run it (that package is a root-only dependency Metro never bundles): `osm-poi` is the POI catalog (`POI_CATALOG`, `categorizePOI`), the Overpass QL builder, corridor chunking/packing and the exact point-to-route geometry; `overpass-client` the spaced, retrying `createOverpassFetcher` (only `fetch`/`AbortController`/timers; `onResponseBytes` counts what came back) and `createFallbackFetcher` (each query tried on several instances, starting with the last that answered); `poi-enrichment` keeps `enrichRoute` and also exposes its steps — `prepareCorridor`, `fetchCorridorGroups` (`only` re-asks just the failed groups), `placePois` (optional `pause` between slices; `indexed` places through `createRouteIndex`, a grid over the route that gives `nearestPointOnRoute`'s exact answer for every POI within the radius at a cost that does not grow with the route's length — about 25× faster on the Heysen, held to the full scan by `osm-poi.test.ts`; off by default, so `fetch-pois` and the phone keep gpx-tools' code path, and on for the comments API's community-route enrichment). `scripts/fetch-pois.ts`, the web's imported-trail search (`src/web/poi-enrich.ts`) and the phone all use these. `scripts/osm-poi-parity.test.ts` holds them byte for byte to `gpx-tools` (catalog, classification, chunks and query text on real trails, placement and `toTrailPOIs` output, the request a fetcher sends): a catalog change belongs in both, and the parity test says which one moved
- `trail-poi-search.ts` - A whole trail's search for an interactive client: `planTrailPoiSearch` (the build's route and corridor, `INTERACTIVE_MAX_VERTICES` 150 per query, and a `PoiSearchEstimate` — queries, km searched, upload, a download range of 0.5-15 KB per km measured on the bundled `pois.json` files) and `finishTrailPois` (placement, `toTrailPOIs`, then the build's passes in the build's order — noise, duplicates, city thinning — and `slimPoi`; `[]` when nothing was found, never `undefined`; `indexed` passes through to `placePois`). The phone and the comments API's community-route enrichment both finish through it. Also `POI_SEARCH_RADIUS_KM` (2, the build's) and `INTERACTIVE_OVERPASS_ENDPOINTS` (overpass-api.de, overpass.private.coffee, overpass.kumi.systems — `maps.mail.ru` left out on purpose: this list decides where a hiker's route outline goes)
- `position-on-trail.ts` - `snapToTrail(lat, lon, points, hintIndex?, breakStarts?)`: the one projection of a position onto a track — the nearest *segment* (not vertex; bundled tracks are thinned to ~900 m spacing on the CDT), a windowed scan around the hint with an exact full scan as fallback, route breaks never snapped across, antimeridian-safe. Returns the segment's start `index`, `currentKm` and `offTrailMeters`; `isOffTrail` / `OFF_TRAIL_THRESHOLD_M` (50 m). Used by the phone's GPS position (`useLocation`, `use-plan-route`), custom routes, waypoint detail and hiker-waypoint placement (`user-waypoints.ts`)
- `point-index.ts` - Uniform-grid nearest-point lookup (`buildPointIndex`, `PointIndex.nearest`) in raw degree space, for answering "which track point is under the cursor?" without scanning a 20,000-point display copy on every mousemove. Platform-neutral, so the mobile map can reuse it; the web trail viewer rebuilds its index wherever `displayPoints` is set
- `types.ts` - TypeScript interfaces, incl. `WaypointAccess` (the off-trail `tn:` fields) and `StoreKind` (`full` | `limited` | `meals` | `none`, `isStoreKind`): what a resupply place sells, from GPX `<tn:store>` (Te Araroa's, upstream) or an `access.json` entry's `store` (`buildTrail`'s `waypointStores`, set on the source waypoint after ids are minted so every row of it carries it). Absent means the data does not say
- `plan-types.ts` - Plan data types shared with mobile. `PlanDocument` (id-keyed stops with `nights`, `note`, `booked`; `resupplyStops`; `resupplyZeroDays`, zero days per resupply stop by option id — half-day steps in 0.5..14, `isStoredZeroDays`, absent rather than empty; `PLAN_LIMITS`) is the one plan shape: the wire body of `PUT /v1/plans/:id`, mobile's `plans.document_json`, the web `localStorage` value and the shared-plan payload. `PlanState` is legacy, read only by the web migration
- `plan-editor.ts` - The pure plan editor both platforms drive (spec: `plans/day-planner.md`): `toggleStop`, `replaceStopsInRange` (applying a suggestion), `setNights`/`setStopNote`/`setStopBooked`, start date and direction, `overnightCandidates`, `computePlanDays` (nights cascade into dates and `restDays`), `splitUnplannedTail` (the stretch after the last stop is "not planned yet" until it fits in a day), `servicesAtStop` over the trail's OSM POIs (1 km, `duplicateOf` included, `undefined` when the trail has no POI data), `refreshStopKms` (moves a stop to its waypoint's current km when a data update moved the place — by id, against the trail as stored, an alternate's stops against that alternate's waypoints; never onto another stop's km — run on every plan load and server copy by both planners: the phone's `GuideView`, the web `plan-viewer` init and `adoptServerPlan`, saving and syncing only a real change; never from trail data older than the plan's `dataUpdatedAt`, the newest data time any save stamped on it (`stampPlanData`/`planDataIsCurrent`) — the phone's copy's `updatedAt`, and on the web the generated JSON's `dataUpdatedAt`, which `build-trails.ts` sets to the app index's `updatedAt` while the committed app file is exactly this build's data and to the build time otherwise (`scripts/lib/web-data-time.ts`); the server refuses a stamp that is not a strict ISO time or is in the future, and clients read a far-future one as none), `setResupplyZeroDays(plan, optionId, days)` (0 removes the entry and the last removal removes the map; same object back for a no-op; `RangeError` off the half-day steps 0..14), `chooseResupplyOption(plan, groups, groupKey, optionId | null)` (one resupply decision group's choice — exactly that option, or none — with every other group left as it was; an absent selection is materialised to every option first, and the choice takes the group's first stored slot so re-choosing is a no-op), `migratePlanState`, `isPlanDocument`. Every editor returns a new document or the same object for a no-op; stop km stay NOBO-absolute
- `plan-alternates.ts` - Taking a trail's alternates in the day planner (spec: `plans/day-planner.md` "Alternates"). `buildPlannedRoute`/`plannedRouteTrail` splice the chosen alternates (`PlanDocument.alternates`, by name; only `type: 'alternate'` with both junctions and no `parent` — `plannableAlternates`) into the main line, giving a trail of the same shape in **route km**, so every planner calculator runs on it unchanged. The document keeps its km contract: a main-route stop is NOBO main km, a stop on an alternate carries `alternate` and the alternate's own absolute km (branch km + km along it). Both planners hold the stored document and edit a route-km view of it (`planToRoute`/`planFromRoute`, `editPlanOnRoute`); a stored stop the view cannot show is carried back unchanged when `planFromRoute` is given the stored plan, so always pass it; `alternateKmToRoute` is null for a km past an end of its alternate (beyond `ALTERNATE_END_SLACK_KM`) rather than clamped to the branch or rejoin, so such a stop is listed by `planStopIssues` instead of drawn where it is not; `stopsHiddenOnRoute` is the stored stops a route view leaves out. `setPlanAlternate` is the one edit that changes the route (drops overlapped alternates and the stops it bypasses, moves a stop whose waypoint id both lines share; a stop the route already left out — past a shortened alternate's end or the trail's, or on an alternate the data no longer has — stays as stored). `planFromRoute` folds a hidden stop into a stop just ticked with its waypoint id: the new stop takes its nights, note and booking, so ticking a stop's own place moves it and never leaves two stops with one id. POIs move to route km too: one found along a taken alternate (`poiVariantFinder` in `poi-display.ts`, the same choice `mirrorPoiDistances` makes) is placed along it from its own km, as the alternate's waypoints are; the rest are read as main-route km, and those on a bypassed stretch are dropped. `alternateMarkers` places the Stops list's branch/rejoin cards. One stop per place is checked per line, client and server
- `plan-stop-issues.ts` - `planStopIssues`: the stored stops the current trail data no longer explains, each with a reason (`waypoint-missing` — its id is not on its line, main route or alternate; `waypoint-moved` — its place moved but another stop already sits at the new km; `off-route` — past an end of the trail; `alternate-missing`; `off-alternate` — past an end of its alternate, `ALTERNATE_END_SLACK_KM` 0.1 km allowed for the build's rounding; `not-on-route` — a bypassed stretch or an alternate the plan does not take; `duplicate`; `newer-data`, every issue when the device's data is older than the plan's `dataUpdatedAt`) and `routeKm`, the route km when it still ends a day there, else null. It never edits the plan: a placed stop keeps ending its day, an unplaced one is listed apart with its nights left out of the dates, and `removeStoredStop` (`plan-editor`) takes one out of the stored document, which a route view's `toggleStop` cannot reach (by waypoint id on its line, so a stop judged on a refreshed copy is still found). Hiker waypoints (`hw_`) are never reported missing — the web never loads them. `stopIssueText`/`stopIssueWhere`/`stopIssuesNotice`/`STOP_ISSUES_HINT` are the shared wording (the notice names a trail data update only when a data-derived reason is present); callers pass `dataUpdatedAt` exactly as they passed it to `refreshStopKms`; both planners show the notice above the days, each stop with its reason and Remove, and the reason on the day card a placed one ends
- `day-suggest.ts` - `suggestDays`: the N best alternative plans for the next K nights from a km, over caller-supplied candidates. It runs a k-best DP ranked by mean squared, range-scaled deviation from distance/ascent/hours targets, and a final walk out to the range end is held to maximums only. The criteria are the hiker's: `assertSearchable` refuses a set with no maximum rather than capping it. Both planners use it: the phone's Next days card and the web plan page's "Plan the next few days" section
- `plan-suggest.ts` - What both planners put around `day-suggest`, so they cannot drift:
  - the hiker's inputs (`SuggestPrefs`: mode, days, options, distance/ascent/hours ranges), their pace-derived starting values (`defaultSuggestPrefs`) and shape check (`isSuggestPrefs`);
  - the two modes as criteria (`suggestionCriteria`);
  - where a suggestion starts (`suggestionStart`: location, else last stop, else section start);
  - `applySuggestedPlan`;
  - the hour bands: `planWindowHours`, `planFloorHours`, and `finalDayMaxHours`, the most hours a plan's last day may take before it is "not planned yet".
- `track-geometry.ts` - Nearest-point lookup and elevation gain/loss between km positions. `calculateElevationBetween` (and `buildTimeIndex` in `day-calculator.ts`) take an optional `breakStarts` set — pass `routeBreakStarts(track.breaks, 'points' | 'displayPoints')` for whichever array you hand them, or a trail with route breaks climbs the gap between landings. When the points carry `cumAscent`/`cumDescent` (`annotateCumulativeElevation`, written into the mobile assets before thinning) both read the difference of the two ends instead of walking the steps between them, and `breakStarts` is not consulted — the break step was already left out of the sums. Summing a thinned track's own steps reported 65-86% of its real climb
- `day-calculator.ts` - Hiking time estimation and day splitting; `buildTimeIndex` reads the points' `cumAscent`/`cumDescent` when they carry them, so it keeps matching `calculateElevationBetween` to the metre on thinned and full-resolution tracks alike. **Stops off the route are walked to**: `placeWalk(waypoint)` is the walk to a place (`offTrailKm` with its climb in, `offTrailAscentM`/`offTrailDescentM`) or null — on the route, a turn-off, or a ride (`hitch`/`shuttle`/`boat`, or an unsaid distance over `WALKED_WHEN_UNSAID_MAX_KM`, 5 km; `resupply-plan` re-exports it). A `PlanStopInput` carrying `walk` adds the walk in to the day that ends there and the walk back out (climb and descent swapped) to the next: `distanceKm`, `ascentM`, `descentM` and `estimatedHours` include it, and the day carries `offTrailKm` and `walkIn`/`walkOut` (absent when it stays on the route; `startKm`/`endKm` stay route km). `computePlanDays` looks each stop's walk up by `waypointId` through `stopWalk`, which gives none to a stop no longer at its waypoint's km (saved before a data update moved the place: that day already walks the old way there). `day-suggest` counts a candidate's `walk` and `fromWalk` (the last stop's walk out, via `SuggestStart.waypointId` and `stopWalk`) the same way, keeping the shortest walk where places share a junction km, and the phone's Stops-list legs (`plan-stops.stopLegs`, walks looked up in the trail's waypoints, not the candidates shown) and Today rows (`today-plan.todayRows`) add up to the same day. All four add walks through `addPlaceWalks`, the one home of the out/in sum
- `resupply-calculator.ts` - Town resupply points and the km between them, and food carry weight (grams per day required, never defaulted); days and the long-carry flag are worked out per leg in `resupply-plan.ts`; which waypoints count comes from `isResupplyWaypoint` in `waypoint-taxonomy.ts`
- `water-carry-calculator.ts` - Water carry distance calculations (the dry-stretch km is the hiker's and required); which waypoints count comes from `isWaterWaypoint` in `waypoint-taxonomy.ts`. A carry is measured as walked: the route km between sources plus the walk back out of the source it starts at and in to the one it ends at (`placeWalk`; the gap's `fromOffTrailKm`/`toOffTrailKm`), and a source another one beats for walking (at the same km nearer the route, or on the route a short way along from a tap down a side valley) is dropped rather than listed as a carry nobody walks
- `resupply-plan.ts` - Resupply *planning*: `resupplyCandidates` (the main route's waypoints plus every town a **side trip** leads to — on the side trip, or an off-route town within 1 km of its far end — offered at the junction with the side trip's length as `offTrailKm`, `accessMode: 'foot'` and its climb in `accessRoute`; call sites pass `resupplyCandidates(trail)`, never `trail.waypoints`) → `listResupplyOptions` (every resupply-family waypoint, grouped by the turn-off you leave the route at) → `resolveResupplyStops` (the ticked ids → stops; `undefined` = every option) → `computeResupplyLegs` (real ascent, Naismith hours, days, food per leg; **requires** `dailyHours` and `baseKmh` and throws rather than defaulting them). Each stop carries its `access` (`StopAccess`: the longest *walk* among its ticked places, else the longest ride), and the walk to a stop **and back** is one side trip counted whole on the leg that *arrives* there (as the hiker's planning spreadsheet does): `sideTripKm` (twice the one-way walk), `sideTripAscentM`/`sideTripDescentM` (the climb in plus the climb back out), so a UI can say "incl. 2.8 km to Salida and back" (`legSideTripText`); the leg out of the stop then starts at the turn-off. A section that starts at a stop does not count its walk out again (the section before, arriving there, already did), so adjacent sections add up to the whole trail; only a stop at the trail's own start (km 0), which no leg arrives at, has its walk back out counted on the leg leaving it. `distanceKm` stays trail km, `offTrailWalkKm`/`walkedKm` add the walking (in the hours, days and food), and `rides` lists the hitch/shuttle/boat km — and a distance whose way the data does not give (all of Te Araroa's) past `WALKED_WHEN_UNSAID_MAX_KM` (5 km; shorter unsaid ones are walked) — which are reported, never timed. **Zero days**: `ComputeResupplyLegsOptions.zeroDays` (the hiker's, by option id, whole or half days ≥ 0; only a stop resolved to one place takes its figure — an undecided stop takes none) puts `zeroDays` on the leg arriving at the stop and counts it in `summariseResupplyPlan`'s `totalDays` — never in `estimatedDays` or `food`, which cover walking days only. **Zero days and the camp plan are independent inputs**: with a camp plan passed (`days`), `arrival` comes from that plan alone — `date` is its date (its stops' extra nights already push it back) and `day` the calendar day that date falls on (walking days plus the rest days before it, so day and date agree) — and resupply zero days are not added on top, which would count the same rest twice. In the editor, zero days follow the selection: `setResupplyStops` with an explicit list (and so `chooseResupplyOption`, for the places a choice leaves out, none included) drops the zero days of every option no longer ticked, `undefined` keeps them, and `resetResupplyPlan` clears the selection and the zero days together. The hiker's figures are stored in `PlanDocument.resupplyZeroDays` (synced; the comments API validates and keeps it — deploy the worker before shipping clients that write it, or the server drops it) and passed straight in as `zeroDays`. `resupply-display`'s `legDistanceText`/`legRidesText`/`legSideTripText`/`stopAccessText` are the shared wording ("52.3 km + 4.0 km off trail") → `summariseResupplyLegs`, and `summariseResupplyPlan` (the planner's headline figures: `stopsChosen`, `longestLegKm` as walked, `mostClimbM`, `longestCarryDays`, `heaviestFoodKg`, `totalWalkingKm` incl. side trips and never rides, `totalDays` = walking days + `zeroDays`). Also `allResupplyOptionIds` and `plannedResupplyIds` (a ticked option plus the point on the route that serves it — the km the food has to reach — and *only* that point: at the CDT's Monarch Pass, ticking Salida must never plan Poncha Springs, the other town on the same hitch), which is what every mobile "planned" surface highlights. A group is **one decision** (go to one of its places, or none): `resupplyGroupChoice(group, selectedIds)` reads it from the stored selection as `{ kind: 'undecided' }` (more than one of its options ticked, the absent every-option default included), `{ kind: 'chosen', optionId }` or `{ kind: 'none' }`; a single-option group is a Yes/No, so the default reads as `chosen`. `chooseResupplyOption` in `plan-editor` writes it
- `resupply-display.ts` - The platform-neutral text of a resupply option: `firstSentence` (abbreviation-aware), `accessSummary` and `resupplySummaryText`, each taking the caller's distance/weight formatter so the web (metric) and the phone (unit preference) share one set of words; `resupplyOptionShortName(option, group)` (drops the trailing "(access: …)" — "Chama (access: Cumbres Pass (CO 17))" → "Chama" — and, inside a decision group, a prefix repeating the group's place — "Monarch Pass (Monarch Crest Store)" → "Monarch Crest Store", only when what follows is one balanced parenthetical, so "Wanaka (Four Square) (closed Sun)" stays whole; UIs keep the full name as the tooltip / accessibility label), `resupplyTurnOffText(group)` (a one-place group's secondary line, "turn-off at Cumbres Pass (CO 17)", from the group label — the data's `accessName` — never parsed from the name), `resupplyGroupName`, `legEndpointNames(leg, groups, selectedIds)` (an end with more than one place still ticked is "<turn-off> (not decided)" — or, with no turn-off label, the ticked places' short names, never an unticked one — instead of every place joined, and a stop at one place goes by its short name; `legSideTripText` takes that name, or `null` for "incl. 0.4 km off trail and back"); `storeLabel(option)` (`STORE_KIND_LABELS`: "Full resupply", "Small store", "Meals / parcel only", "No shop", and "Box only" for a `none` place with `acceptsBoxes`; null when the data does not say)

**XML adapters:** GPX parsing is injected, not hard-wired, so one parser serves three runtimes. `parseGpx` defaults to `DOMParser` (web); build scripts pass `jsdomXmlAdapter` (`scripts/lib/xml-adapter-jsdom.ts` — jsdom must never reach `src/lib`); mobile passes `fxpXmlAdapter` (`src/lib/xml-adapter-fxp.ts`). A parity test (`src/lib/xml-adapter.test.ts`) asserts the fast-xml-parser and DOMParser backends produce deep-equal `GpxData` for every fixture.

**Ingestion is shared, not forked:** `scripts/build-trails.ts` and `importGpx` both call `buildTrail`, so a GPX file produces the same trail in the build, on the web and on the phone. The build script keeps only what needs a file system: CalTopo GeoJSON, the CSV waypoint fallback, climate, curated descriptions, the `data/waypoint-ids.json` registry, and HTML generation — each passed in as a hook. Any change to `trail-ingest.ts` must leave `public/data/generated/*.json` byte-identical unless the change is intentional.

**Shared calculators:** `track-geometry.ts`, `day-calculator.ts`, `resupply-calculator.ts`, `resupply-plan.ts`, `resupply-display.ts` and `water-carry-calculator.ts` are the single implementations used by both web and mobile. Mobile imports them via the `@lib` alias (Metro `watchFolders` + tsconfig paths + Jest `moduleNameMapper`). Parameter types are structural (e.g. `PlanWaypoint`, `PlanStopInput`) so each platform's own trail/waypoint/stop shapes are accepted without conversion. On mobile the Plan screen edits a saved `PlanDocument` through `@lib/plan-editor` (SQLite `plans`, `state/plans-store.ts`); nothing writes stops on its own. The Next days card (`features/plan/NextDaysCard.tsx` + `plan-suggest.ts`, over `@lib/day-suggest`) offers ranked alternatives for the next few nights from the GPS km or the last stop, by hours & pace or by distance/climb/hours ranges (per-trail inputs in `plan-inputs-store` `suggest`). Applying one replaces only the stops inside its window. Pace and daily hours stay per trail in `plan-inputs-store.ts` (device-local, not part of the document — a shared plan should not say how fast its author walks); the resupply selection is `PlanDocument.resupplyStops`, edited through `setResupplyStops`, with a legacy `plan-inputs-store` selection read only while the document has none. The adapters live in `mobile/src/features/plan/plan-adapters.ts`. Pace presets (`Pace`, `PACE_KMH`) live in `plan-types.ts` so the two platforms cannot drift.
