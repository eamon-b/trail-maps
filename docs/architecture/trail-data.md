# Trail data (`data/trails/`) and generated data

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

Each trail has its own directory containing:
- `*.gpx` - Original GPX track data
- `trail.json` - Trail metadata and build config (name, `country`/`states`, `gpxFile`, `dataSource`, `trackClassification`, climate locations, POI rules); the waypoints themselves come from the GPX (and, where `geojsonFile` is set, a CalTopo GeoJSON export, which types each GPX waypoint by the folder of the nearest marker of the same name: the guides pin a campsite and its water, or a hut and the camp beside it, under one name). A waypoint is renamed in both files, under the same prefix (`C `, `W `, `WT: `)
- `climate.json` - Climate data for locations along the trail
- `pois.json` - Optional OpenStreetMap points of interest along the trail, written by `fetch-pois.ts` and folded into the generated JSON's `pois` array by `build-trails.ts`. POIs are kept **separate from waypoints**: they are never merged into `waypoints` and never enter `data/waypoint-ids.json`. Shape: `{ source, attribution, fetchedAt, searchRadiusKm, endpoint, rejected, duplicates?, pois }`, where `pois` holds everything fetched (sorted by `distanceAlongTrail`, then key) and `rejected` is a hand-edited list of `<type>/<id>` keys the build drops — typically a place found closed on the ground that OSM still lists (Shikoku's FamilyMart `node/270408582`); every entry must be a `<type>/<id>` key (a malformed one fails the build rather than silently hiding nothing), and the build warns about a rejected key that matches no fetched POI, which is the cue to drop it. Only a fetch that replaces the file (a clean whole-trail run, or `--force-replace`) can trigger that: a merge (`--from-km`, including the `--from-km 0` maps.mail.ru recipe, or a run with failed chunks) keeps the stored copy, so the key keeps matching. `duplicates` (optional, hand-edited) maps `<type>/<id>` to the waypoint id that POI is the same place as, for pairs no rule should match — a nickname (the AAWT's `Schlink Hilton` is Schlink Hut) or a campground's second name; the build flags them like a rule match, warns about a key that matches no POI (deleted from OSM, `rejected`, or dropped as noise) and about one that replaces a different rule match, and fails on a waypoint id the trail lacks. A re-fetch carries `rejected` and `duplicates` over unchanged, so review work survives a refresh. The file is the raw fetch: three build-time passes sit between it and the shipped JSON — `@lib/poi-noise` drops category-wide noise (bus stops other than walkers' shuttles, picnic shelters and pergolas, hospitals tagged `emergency=no`, help phones on motorways and in road tunnels), `@lib/poi-dedup` flags POIs a curated waypoint already covers — matched against every waypoint the trail has (`dedupCandidates`: main route, off-trail, alternates, side trips and termini), and against a generic `poi`-typed one only when the two are within 10 m with the same name, names are compared without diacritics (`Pāhautea`/`Pahautea`) and with `Mt`/`Nth`/`Sth`/`N`/`S`/`E`/`W` expanded, within 25 m a name score of 0.85 is enough (spelling drift: `Edmonsons`/`Edmondson Hut`), a name with a word the other lacks from `old`/`new`/`upper`/`lower`/north/south/east/west, or with different numbers on both sides, is never a match (`Old Aparima Hut` is not `Aparima Hut`), an unnamed `camping` POI within 30 m of a compatible waypoint (the tent area OSM maps beside a hut: the AAWT's Pockets Hut) counts as that waypoint's even with no name to compare (as does one named only with generic words, `Campsite`), unless a second, differently named compatible waypoint is no more than 30 m further away (the Overland's Waterfall Valley camp site, between the old hut and the group platform); other unnamed POIs never do, nor does a name in a script the matcher cannot read (Shikoku's `遍路小屋`), and `@lib/poi-urban` thins cities: where POIs run over 15 per km of trail (seeded there, grown out through suburbs at half that, at least 40 POIs) it keeps only the first and last of each category, anything flagged `duplicateOf`, and "anchors" — supermarkets, convenience stores (Japan's resupply: the Shikoku henro's konbini), outdoor shops, post offices, campgrounds, huts, hospitals with `emergency=yes`, stations, ferry terminals — one per kind per 2 km, branded first. That took Te Araroa from 8,790 shipped POIs to about 2,100 (Auckland 3,166 → 50), and also thins Albany (Bibbulmun), Albury (Hume and Hovell) and Jackson (CDT); small trail towns stay whole. All three run at build/import time, never at fetch time, so changing a rule is a rebuild rather than another slow Overpass run. A trail can add rules of its own in `trail.json` `pois` (`TrailPoiConfig`): `exclude` drops OSM `key=value` tags that are no use on that trail (Shikoku drops `amenity=post_office` and `amenity=fuel`; a POI that is also `shop=convenience`/`supermarket` is kept), and `keepInCities` exempts a tag within `withinKm` of the route from city thinning (Shikoku keeps every konbini within 500 m: one per 2 km hid 19 of the 40 a pilgrim walks past in Tokushima). `build-mobile-trails.ts` ships them to the app slimmed through `@lib/poi-display` `slimPoi` (display tag keys only, rounded coordinates, no `duplicateDistanceM`). See `scripts/lib/trail-pois-file.ts`.
- `access.json` - Optional: where each off-route waypoint is walked to from, by waypoint id (`scripts/lib/trail-access-file.ts`), written by `fetch-access.ts` and applied by `build-trails.ts` with no network. `method` `osm` (found: `junction`, `junctionKm`, `offTrailKm`, climb in, the walk's `path`, and `straightLineM`/`nearestKm` — what the build did without it), `manual` (hand-written `junction` + `offTrailKm`; a re-fetch never touches it, so correct OSM here) or `none` (`reason`; the place keeps its nearest route point and is walked as the straight line). Any entry may also carry **`store`** — what a resupply place sells: `full` (supermarket or grocery), `limited` (general, convenience or camp store), `meals` (cafe, pub, lodge: food to eat there, perhaps a parcel, nothing to carry out) or `none` (no shop) — written by hand from the place's description and left out wherever the description does not make it clear (`StoreKind` in `src/lib/types.ts`; the planner's words are `storeLabel` in `resupply-display.ts`, "Box only" for a `none` place that takes boxes). A place with no walk to route (on the route, or given its distance by its source — every CDT turn-off and town) takes a **store-only** entry, `name` + `store` and no `method`; the build gives every row of the waypoint (main route, off-trail, alternate, side trip) its `store` through `buildTrail`'s `waypointStores` and nothing else, and `fetch-access` never routes one, keeps it through a re-fetch, and carries a re-fetched entry's `store` over. Te Araroa's `store` comes from upstream instead (`<tn:store>` in its GPX, beside `<tn:acceptsBoxes>`), so its file carries none. No file means `fetch-access` found no candidate (Overland), not that it was never run: a run with nothing to route writes none (and removes an old one, unless it holds store-only entries), and a run whose every query failed writes none and exits 1. The CDT's file holds store-only entries alone, which says nothing about routing. `fetchedAt` is the oldest Overpass answer the entries rest on, cached or kept. Review a re-fetch by its diff: a `junctionKm` far from `nearestKm` is a place that moved. An entry with `variant` (an alternate's name) is a place walked to from that alternate, not the main route — its `junctionKm`/`nearestKm` are km along the alternate from its start, and the build lists it in that alternate's `waypoints` at `startDistance` + `junctionKm` (Heysen's Quorn and Hawker places, Shikoku's Cotton Field Campground, two Te Araroa bypass campsites)
- `descriptions.json` - Optional curated waypoint descriptions (sources for every fact: `plans/waypoint-description-sources.md`), keyed by the stable ids in `data/waypoint-ids.json`. `build-trails.ts` applies them to the bundled trail JSON (overriding any GPX/GeoJSON text); `upload-descriptions.ts` pushes the same file to the comments API, where mobile syncs it as an override (`synced ?? bundled`). The prose is factual and non-prescriptive — it describes the place and its water, never instructs the walker or addresses them as "you". See `scripts/lib/waypoint-descriptions.ts`.

A trail may also carry `Terminus: <name>` tracks — alternative starts/finishes, declared with `trackClassification.terminusPatterns` and drawn junction-first, with a `<wpt>` of `<type>endpoint</type>` at the free end. `buildTrail` attaches the one junction at whichever end is actually nearer the route (turning the line round if the generator drew it backwards), attaches the nearby waypoints including that endpoint to the variant, and keeps the endpoint out of `offTrailWaypoints` so a place the route reaches is never also listed as a place it misses.

A main route that doubles back on itself for 2 km or more makes the build warn (`detectSelfRetraces`). A walk into town that is not the route is lifted out with `extractSpurs`; start and end the range at the fork (where the out and back legs meet, not where the retrace warning starts), and to keep the town a stop give it an `access.json` `manual` entry (junction = the fork, `offTrailKm` = the spur's one-way length, climb as the build measures the spur) — the Bibbulmun's Collie, 2.2 km from the line, is set up this way. A retrace that *is* the route as drawn goes in `knownRetraces` (`turnaroundKm` and `lengthKm` as the warning reports them, matched within 1 km and 15%, one entry per retrace, and a `note` the build logs instead): the Bibbulmun walks into Denmark on the official line to the Wilson Inlet ferry, then back out to wade the inlet mouth.

A route that passes the same place twice matches its waypoint twice, and the build fails on the repeated id (the minter runs before the fan-out, so it cannot tell a real second pass from a waypoint matched by mistake). An out-and-back goes in `extractSpurs` as above. A route that genuinely comes back the way it went, days later, sets `"revisitedWaypointIds": "suffix"`: every pass is listed, and the later ones get `<id>_2`, `<id>_3`, as imported trails do, so each pass takes its own comments. Three Passes uses it: it walks back down through Namche and the Dudh Koshi villages to Lukla, and passes Lobuche either side of Gorak Shep. Its store-only `access.json` gives every teahouse village `meals`, Kharikhola and Jorsalle `limited`, and Jiri, Namche and Lukla `full`; its `maxJunctionDistanceMeters` of 150 keeps the Ama Dablam Base Camp side trip, whose far end is 175 m across the valley from the route, from being read as a connector. It has no `pois.json` yet (Overpass timed out).

Te Araroa's file also carries waypoint types no other trail uses. `gap` is the "Trail ends"/"Trail resumes" pair at each route break. The **turn-offs** are points on the route at the km you leave it for a place that is somewhere else, typed `<servedType>-access` — `town-access`, `hut-access`, and so on — so one field says both what kind of place it is and that you are not there yet.

Two rules follow, both in `waypoint-taxonomy.ts`:
- `RESUPPLY_TYPES` lists `town-access`/`food-access`/`resupply-access`/`teahouse-access` **one by one** rather than stripping the suffix generically. A `water-access` must never satisfy `isWaterWaypoint` — that would tell the carry calculator there is water on the route when it is down a side road, and under-reporting a dry stretch is the dangerous way to be wrong.
- `baseWaypointType()` is the fallback for every map keyed by type: `MAP[type] ?? MAP[baseWaypointType(type)] ?? FALLBACK` gives a turn-off its served type's icon, colour and chip without seven more entries per map. Use it rather than enumerating; `isAccessWaypoint()` is there for the cases where a turn-off must behave *differently* from the place (you cannot sleep at one — see `overnightWaypoints`).

Changing a bundled waypoint's `type` re-keys it in `data/waypoint-ids.json`, which matches on type + 100 m proximity: the ids churn silently and any server-side comment keyed to them is orphaned. Migrate the registry entries in the same commit. A waypoint whose exact name is on a nearby entry claims it before any proximity match (nearest pair first across the trail), so a newcomer of the same type within 100 m of an existing waypoint mints its own id instead of taking that one's; when it does, the build warns, naming the waypoints beside it (one place entered under two names looks the same), and repeats the warning at the end. It warns only on the build that mints: from then on the newcomer claims its own entry by name, so check the warning before committing the registry. A newcomer with the *same* type and name within 100 m stops the build — the registry cannot tell a second place from the first entered twice — so give two such places distinct names. So does a pair of same-name waypoints that have both moved and are each in range of the other's entry, since nearest-first could swap their ids: set the entries' coordinates in the registry by hand. An entry no waypoint matches in a build is kept but marked `retired: true`; a retired entry is reclaimed only by a waypoint of the same type, within range, with the exact same name, so a new place built near a removed one never inherits its id, comments or description.

**Te Araroa is not curated here.** Its route, waypoints and resupply points are built in [te-araroa-data](https://github.com/eamon-b/te-araroa-data), which commits its outputs; this repo takes them as a devDependency pinned by `package-lock.json`. `npm run sync:te-araroa` copies `te-araroa-sobo.gpx` out of `node_modules` into `data/trails/te_araroa/`, where it is gitignored — only `trail.json` and `climate.json` are committed. `npm run build` runs the sync first, so a fresh clone (or Vercel) builds without a manual step. `npm update te-araroa-data` takes a newer build. Do not hand-edit the GPX: it will be overwritten, and the fix belongs upstream.

**Open-data trails.** Eleven Australian trails come from open data rather than a guidebook, and each `trail.json` `dataSource` names its dataset and licence: the Great Ocean Walk and Great South West Walk from Great Trails Victoria (CC BY 4.0, waypoints included); the Overland, Three Capes and South Coast tracks from the Tasmanian LIST Transport Segments layer (CC BY 3.0 AU) with OSM waypoints; the Great North Walk, Six Foot Track, The Coast Track, Grampians Peaks Trail, Kep Track and Thorsborne Trail from OSM route relations (ODbL). Their `<ele>` is Copernicus GLO-30 sampled every 30 m and smoothed over five samples before it was written, because the build sums every delta and raw surface-model samples read forest canopy as climb (the Great South West Walk read +6,220 m raw, +3,400 m smoothed). The GPX files were generated once and are the source of truth here; the generator is not committed. Their waypoints have since been reviewed by hand (2026-10: towns and trail ends added, duplicates and non-public camps removed or retyped `poi`, names fixed), so a regeneration would lose that review — diff the waypoints against the committed file before replacing one. Where their climate locations sit off the trail's height (a river camp under a slope, a range crossing the terrain model smooths down, a coastal point on a sea cell), `climateLocations[].elevation` makes `fetch-climate.ts` correct the temperatures to that height. The six guidebook trails' locations were checked the same way in 2026-10: points on sea cells, up to 14 km off the line or hundreds of metres below the ground they stand for were moved onto the trail, and unrepresented high ground (Baw Baw, Paddys River Dam, Brinkley Bluff) was added.

## Generated Data (`public/data/generated/`)

Built at build time:
- `index.json` - Trail index (the landing page's list): `id`, `name`, `shortName`, `lengthKm`, `region`, `country`, `states`, `featured` when true, and `start` (the route's first point, 5 decimals) for the landing page's map overview. The mobile index copies only the fields it names, so `start` stays web-only
- `{trail-id}.json` - Processed trail data with simplified tracks
