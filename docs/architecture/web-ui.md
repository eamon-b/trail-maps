# Web UI (`src/web/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

**Name and address.** The site and the app are both **Tracknotes**, and the site is served at `https://tracknotes.info` (the Vercel project; `trail-maps.vercel.app` is retired and nothing keeps it working). Every page title ends ` - Tracknotes`. The origin is written down in two places that must move together: `SITE_ORIGIN` in `src/lib/contribution-licence.ts` (the privacy and terms links the app and store listings use) and `SITE_BASE` in `workers/comments-api/wrangler.toml` (shared-plan links). Browser storage keys are `tracknotes-*` (theme, list filter, POI filter; the theme key is also read by the pre-paint script in every page's `<head>`). "Trail Maps", the site's old name, survives only in the GitHub repo name (and the links and checkout paths that name it) and `data/trails/cdt/cdt.gpx`, which is copied from the `cdt-data` package. Renaming those is tracked in #260.

- `index.html` / `index.ts` - Landing page: filter bar (search, length chips, sort; `localStorage` `tracknotes-list-filter`), Featured (hidden when empty), curated trails grouped Country → State in collapsible sections, Community routes (only when `VITE_API_BASE_URL` is set, Verified/Unverified badges; the list has a 10 s deadline, after which the tier shows its error note), My trails (IndexedDB) with a "Shared by me" block when the API is set and the browser is linked: the reader's own routes from `listMyCommunityRoutes` (same 10 s deadline, fetched in parallel; failures stay inside the block; a 401 clears the session and offers the link form), hidden ones with why (`hiddenReasonText`) and the review summary. "On the map" (`landing-map.ts`, issue #163) follows the Community section's rule (shown only when the API is set; a failed list still shows the curated markers): one circle marker per curated trail (index `start`) and community route (summary `start`, else its bbox centre) the filter keeps, popups linking to each page; no track is downloaded. Leaflet (the trail pages' unpkg build and SRI hashes) is injected only when the map nears the viewport (IntersectionObserver), longitudes are unwrapped so the fit is Pacific-centred when that is tighter, and marker colours are theme tokens restyled on `onThemeChange`. Rendering is pure and tested in `index.test.ts` and `landing-map.test.ts`; styles in `trail-list.css`
- `styles.css` - Global styles and the light/dark theme tokens
- `theme.ts` - Light/dark/system theme: applies `data-theme` to `<html>`, renders the toggle, and exposes `onThemeChange()`/`themeColor()` so canvas and Chart.js code can follow the theme
- `trails/trail-template.html` - Template for individual trail pages
- `trails/trail-viewer.ts` - Interactive trail viewer (map, elevation profile, waypoints). The main route is one Leaflet polyline per stretch on the default SVG renderer: Polyline's `smoothFactor` already runs Douglas-Peucker in screen pixels per reprojection, so a 20,000-point line costs the browser no more vertices than the zoom can resolve. Map hover goes through `@lib/point-index` — set `displayPoints` only via `setDisplayPoints`, which rebuilds that index. The waypoints table ("datasheet") filters to the water or food/resupply family via `@lib/waypoint-taxonomy`; when filtered, the leg columns are recomputed between *visible* rows so resupply-leg distances read directly off the table. Row interaction is delegated from `#waypoints-container`, not the tbody, because every re-render replaces the tbody. The map's expand button (under the zoom control) makes `#trail-map` a fixed full-window overlay (`.is-expanded`; Esc exits), a CSS overlay rather than the Fullscreen API, which iOS Safari only grants to video. OSM POIs start switched off on the web (`defaultWebPoiFilterState` in `trail-pois-ui.ts`) until the hiker ticks the master switch, which is remembered; the phone keeps the shared `defaultPoiFilterState` (on). A POI flagged `duplicateOf` a waypoint is never drawn or listed, but its tags show in that waypoint's marker popup (main-route, off-trail and terminus-end markers, and the planner's popups too; the trail page draws no markers for other alternate or side-trip waypoints, so POIs flagged against those show only on the phone) as a collapsed "From OpenStreetMap" `<details>` (`trail-pois-ui.ts` `waypointOsmDetailsHtml`, as on the phone's waypoint screen); the trail page binds its waypoint popups as functions, so they are built on open and pick up POIs the imported-trail page's enrichment adds later
- `trails/trail-export.ts` - The text of the trail page's two downloads (datasheet CSV and GPX), kept out of the viewer so the formats are testable without a map; guards CSV cells against spreadsheet formula injection
- `trails/climate-template.html` - Template for climate data pages
- `trails/plan-template.html` - Template for plan visualization pages
- `trails/plan-shell.html` - The one copy of the plan page's `#plan-shell` markup (header + three panels). `build-trails.ts` inlines it into `plan-template.html` and the `plan-shell` Vite plugin inlines it into `my-plan.html` at the `<!-- @plan-shell -->` marker, with per-page header fills from `scripts/lib/plan-shell.ts`
- `trails/plan-viewer.ts` - Interactive plan viewer. The header's pace preset and hours/day inputs are persisted per browser in `PlanUiPrefs` (`trail-plan-ui-<id>`, see `plan-state.ts` below; never in the plan document) and feed both `computeDays` and the Resupply tab's legs — the page fixes neither figure. Planned resupply stops are marked on every surface of the page, not only in the Resupply tab: `refreshPlannedResupply()` resolves `@lib/resupply-plan`'s `plannedResupplyIds` once per render, and the day cards, Stops rows, datasheet rows (day boundaries matched on km), map markers and profile ticks all read that one set. `null` — no explicit selection — marks nothing, which is why the every-option default of a fresh plan is not painted as a plan. Alternates: the page holds `storedPlan` (what is saved and synced) and `plan`, its route-km view over `routeTrail` (`@lib/plan-alternates`); `activeTrail()` reverses `routeTrail`, `applyEdit` converts an edit back, and `setAlternate` changes the route. Stops a data update left without a place (`@lib/plan-stop-issues`, judged against `trail` on every render with the same `dataUpdatedAt` `refreshStopKms` was given — null when the data has no publish time) get a notice at the top of the Days and Stops lists — each stop, its reason, the day it ends or that its nights are out of the dates, a Remove button (`removeStoredStop` on `storedPlan`) and the shared hint (ticking an unplaced stop's own place moves it there, via `planFromRoute`) — and a badge on the day card a placed one ends. The Stops tab draws the branch/rejoin cards, the map draws the planned route as the base line with every alternate dashed beside it. The map offers the same take / stay choice as the Stops cards, as the phone's waypoint screen does: clicking an alternate's line opens its popup (`variantPopupContent`, over a 10 px invisible hit line that is off the map while the alternate is taken, so the day lines along it keep their clicks; `renderAll` closes the popup, which would otherwise show the plan as it was), and a waypoint popup lists any alternate that leaves or rejoins within 0.25 km of the place, or the taken one it is on (`alternatesAt`). Opened with `?focus=<optionId>` (the resupply page's "show on map"), it starts on the Resupply tab with the map centred on that option (its turn-off on the route when the map has no marker for it) and the row outlined, then drops `focus` from the address (`history.replaceState`) so a reload keeps the hiker's tab. It follows the resupply page's saves (`storage` event) and writes through `plan-edit-queue.ts`
- `trails/resupply-template.html` / `trails/resupply-page.ts` / `trails/resupply-view.ts` (+ `resupply-page.css`) - The resupply page, `trails/<id>/resupply.html` (generated by `build-trails.ts` like `plan.html`) and `my-resupply.html?id=…` (+ `my-resupply.ts`, an imported trail from IndexedDB). The numbers and the options, no map: modelled on the owner's spreadsheet planner, one table row per candidate stop in active-direction order — km, stop (type, "show on map" link to the planner at `?focus=<optionId>`), store (`storeLabel`, blank when unknown), off-trail km one way, access (on trail / walk / hitch / shuttle / boat, from `optionAccess`), boxes, the choice, zero days, the leg *arriving* there from the previous chosen stop (walked km with `legSideTripText`/`legRidesText` under it, ascent, descent, days with a long-carry flag, food kg) and services (the POI strip, for places within 1 km of the route) and notes (`firstSentence`, full text in a `<details>`). A group with one option is Yes/No; a decision group (several towns from one turn-off) is a tinted block of radios plus "None – carry through", written with `chooseResupplyOption`, its options named by `resupplyOptionShortName` (as is every row: "Chama", not "Chama (access: Cumbres Pass (CO 17))", the full name as the tooltip; a one-place turn-off's secondary line says where it leaves the route, `resupplyTurnOffText`), and a stored `undecided` state (more than one ticked, the every-option default included) says "Not decided yet", with the leg the calculator then counts on the group's header row; leg ends go by `legEndpointNames` ("from Monarch Pass (US 50) (not decided)", and no place named in that leg's side-trip line). Zero days are a 0.5-step input on each chosen stop, stored in the document as `resupplyZeroDays` via `setResupplyZeroDays` and passed to `computeResupplyLegs` as `zeroDays`; the page passes no `days` and shows no arrival dates, so zero days are counted once, by `summariseResupplyPlan`, whose figures fill the summary strip above the table; beside its open-decisions warning, Clear choices (shown once there is a selection or a zero day, as on the phone) goes back to "no plan made" with `resetResupplyPlan`, dropping both. Pace, hours/day, food g/day and the long-carry threshold are inputs on the page, read from and written to the planner's per-browser `PlanUiPrefs`. It edits the same document as the planner (`plan-state.ts`, `plan-sync.ts` with the dialogs mounted from `plan-sync-markup.ts`), follows a planner tab's saves through the `storage` event (`planStorageKind`) as the planner follows its (see `plan-edit-queue.ts` below), keeps the focused control and the opened descriptions across a redraw (it redraws after the browser's focus move, so Tab out of a zero-days box or an arrow key between a group's radios stays put), shows a zero-days entry it could not take (`validity.badInput`, or past the limit) as invalid with the stored value back, and reads the planned route (alternates) and direction as the planner does; it only edits fields keyed by option id plus the direction, never a stop km. `resupply-view.ts` is pure (view model + markup, every data string through `escapeHtml`) and tested in `resupply-view.test.ts`; the wiring in `resupply-page.test.ts`. Below 760 px the table rows stack into labelled cards (`data-label`). Linked from the planner's Resupply tab (`PlanViewerOptions.resupplyPageHref`) and from the trail pages beside "Plan this trail"
- `trails/plan-sync-markup.ts` / `trails/plan-sync.css` - The one copy of the sync arm's link dialog and share panel (filled into `plan-shell.html` at `{{PLAN_SYNC_DIALOGS}}` by `inlinePlanShell`, mounted at runtime by the resupply page) and their styles (imported by `plan-page.css` and `resupply-page.css`)
- `trails/plan-edit-queue.ts` - Keeps the planner and the resupply page, open side by side, from overwriting each other: each page records its edits as functions of the document (`PlanEditQueue.record`), replays its unsaved ones on a copy the other tab saved (`rebase`, on the `storage` event) and, at save time, on whatever storage holds if it moved since (`resolveForSave`), so it never writes a stale whole document; prefs are saved as a patch onto the stored ones (`updatePlanUiPrefs`). A page whose markup was replaced stops writing (`pageIsLive`)
- `trails/stop-services.ts` - The six-glyph services strip (`servicesStripHtml` over `servicesAtStop`), shared by the planner and the resupply page
- `trails/plan-next-days.ts` - The plan page's "Plan the next few days" section, at the top of the Days tab: the web half of the Next days feature (issue 81), over `@lib/plan-suggest` + `@lib/day-suggest`.
  - It starts from the last stop, the trail start, or the browser's location. "Use my location" snaps the fix to the track and shows a "You are here" divider in the Stops tab.
  - It ranks the alternatives. The best is previewed on the map as dashed day lines with numbered flags, and "Use this plan" applies one.
  - It talks to the viewer through `NextDaysHost`, and is removed on a read-only (shared) page.
  - The page also shows the tail after the last stop as a dashed "Not planned yet" card, not a day, via `splitUnplannedTail`.
- `trails/plan-state.ts` - Plan state management: the `PlanDocument` under `trail-plan-doc-<id>`, the one-off migration of the legacy `PlanState` (`trail-plan-<id>`, left in place), and `PlanUiPrefs` under `trail-plan-ui-<id>` — the Stops tab's "show all" switch, the header's pace and hours/day, the planning thresholds (dry stretch beside the water carries, food per day and long carry in the Resupply tab), and the next-days inputs (`suggest`). Pace and hours are per browser, not part of the document (the phone keeps its own in `plan-inputs-store`), and the migration carries a legacy save's values into the prefs. `loadPlanState` rejects a record whose *shape* is wrong, but drops only an unusable `pace`/`dailyHours`. The inputs' initial values and parsing (`INITIAL_PACE`, `INITIAL_DAILY_HOURS`, `DAILY_HOURS_RANGE`, `prefPace`/`prefDailyHours`/`prefThreshold`, `parseDailyHours`/`parseThreshold`) live here so the planner and the resupply page read the same figures
- `upload.html` / `upload.ts` - User GPX import: drag-drop → `importGpx` → report (+ optional elevation backfill) → IndexedDB
- `how-import-works.html` - "How your file is processed" page; the article body is `docs/gpx-import.md`, rendered at build time by the `gpx-import-doc` Vite plugin (GitHub-style heading ids, so `#anchors` against the doc keep working)
- `my-trail.html` / `my-plan.html` (+ `.ts`) - Trail/plan pages for imported trails, booted from `?id=` via `imported-trails-db.ts` and the viewers' `preloadedTrail` argument; "Export for Tracknotes" handoff
- `trails/plan-sync.ts`, `api/` (`client.ts`, `session.ts`, `plans.ts`) - The plan page's sync arm, on only when `VITE_API_BASE_URL` is set (the comments/plans API origin; public, ships in the bundle; unset = local-only planner with the Sync/Share controls removed). A browser links to the phone's identity by entering the code the phone mints (Settings → Linked browsers); the linked token lives in `localStorage` `tracknotes.webSession`, only ever rides in the `Authorization` header, and can be unlinked from the page. Imported (`u_`) trails never sync
- `shared-plan.html` / `shared-plan.ts` - Read-only view of a shared plan (`?s=<shareId>`, public `GET /v1/shared/plans/:id`), with "Open in Tracknotes" (`tracknotes://plan/<shareId>`) and "Copy to my plans". A plan on a community route (a phone syncs those) loads the route from the API's detail and public `trailUrl`, as `community-route.html` does, and offers no copy, since this site has no plan page for a route. The worker's `SITE_BASE` var builds the share URL and must point at the deployed site
- `api/community.ts` - Typed client for the community-routes API; `listCommunityRoutes` returns null without `VITE_API_BASE_URL`, takes an abort `signal` and drops list entries of the wrong shape (`isCommunityRouteSummary`); `checksFromError` reads a 422's server checks and `duplicateRouteId` a 409's `existingId`. `community-ui.ts` holds the check list, region picker and `localCopyId`; `community-labels.ts` holds the status explanations, the status badge (`statusBadgeHtml`), `hiddenReasonText`, `multilineHtml` and `placeLabel`/`regionLabel` (all re-exported by `community-ui`), kept apart so the landing page does not load `@lib/gpx-import`; `link-browser.ts` is the inline link-code form (over `api/session.ts`) for pages other than the planner. `linkDevice` throws `SessionStorageError` (after revoking the new token) when storage refuses the session, and every page uses the session handed to `onLinked` rather than reading storage back
- `community-share.ts` - The upload page's opt-in "Share with the community" step, loaded lazily after a save when the API is set: live `@lib/community-checks` (given the GPX text as `meta.gpxText` whenever it will be sent), CC0 confirmation with the shared licence and privacy lines under it (`renderContributionLicence` in `community-ui.ts`, over `@lib/contribution-licence`; the route page's owner Edit form shows them too), an "Include the original GPX file" box (on by default; the raw GPX goes as base64 only when ticked and ≤ 5 MB), the worker's own message for 409/413/429 (a 409 that names the caller's own route links to it), 401/422 handling. `open()` resets every field for each import. Sharing needs a linked browser (the phone's identity)
- `community-route.html` / `.ts` - Public `?id=c_…` page: detail from the API, trail from `trailUrl`, drawn by the trail viewer as `preloadedTrail`. Report (linked browser; not offered to the owner; kept when only the track download failed), "Save to my trails" (IndexedDB under a `u_` id, so plan sync stays off), "Export for Tracknotes", owner Edit/Delete with checks and the AI review (kept in the no-track view of a hidden route, whose header also says why it was hidden); an owner's edit updates one shared detail that Save, the export and the viewer (`setTrailName`) read
- `admin-community.html` / `.ts` - Unlinked, noindex review queue for admins (AI-rejected/hidden first): Verify / Unverify / Hide / Restore / Re-run review / Delete
- `admin-moderation.html` / `.ts` - Unlinked, noindex moderation page for admins: reported or screen-flagged comments and shared hiker waypoints (hidden first, then those the automated review would remove or wants a human for, then by reports), each with its reports' reasons and details and the automated review's verdict, confidence, categories and summary ("Hidden by the automated review" when the review hid it; `docs/architecture/workers.md`, "comment and waypoint review"): Restore / Delete / Ban author / Ban and remove all their posts / Unban
- `imported-trails-db.ts` - IndexedDB store (`tracknotes-imports`) for imported `ProcessedTrail`s; `index.html` lists them under "My trails"
- `web-utils.ts` - `escapeHtml`, `getQueryParam` — every user-supplied string (trail names) must go through `escapeHtml`
