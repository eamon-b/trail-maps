# Cloudflare workers (`workers/`)

Moved out of `CLAUDE.md` (issue #160) so the per-module detail is read on demand rather than loaded into every session. `CLAUDE.md` keeps the commands, the rules and a pointer here; keep this file in step with the code it describes.

## Comments API Worker: community routes (`workers/comments-api/`)

`src/community.ts` / `src/community-review.ts` (migrations `0005`, `0006`; `0009` for POIs): D1 `community_routes` + `community_route_reports`. A submit re-runs `@lib/community-checks` (with the uploaded GPX as `gpxText`, for the `speed` check) and stores *its* rebuilt trail, never the client's JSON, with `config` rewritten server-side (id, name, `source: 'community'`, country/states, description, CC0 `dataSource`). The bucket has no private area (all of it is served at `PHOTOS_PUBLIC_BASE`), so private objects live at unguessable keys recorded in the row and never returned: the canonical trail JSON at `community/private/<id>/<32 random hex>.json` (`private_key`) and the optional raw GPX (≤ 5 MB) beside it as `.gpx` (`gpx_key`; a file whose head is not `<gpx` is dropped, not refused). While a route is live, a public copy of the same bytes sits at `community/v1/<id>.<md5[0..12]>.json` (`r2_key`; `max-age=300`, so an edge copy outlives a hide by minutes, not a year). An owner's edit writes new objects, keeps the public version it replaced (cached lists still name it) and purges older ones; a de-attribution purges the old public versions at once, since they name the deleted account; hiding a route (AI review, reports or admin) deletes every object under `community/v1/<id>.` and NULLs `r2_key`, so owner/admin detail of a hidden route has `trailUrl: null`; an admin restore from hidden always republishes from the private copy (if it is gone: 404 when removed meanwhile, 409 `conflict` when the row changed, else 500 `trail_missing`), and a hide re-reads the row after its purge and republishes a route a restore made live meanwhile; removal purges both prefixes. Every row change sets `updated_at` strictly later than the value it read (`stampAfter`); an owner's PATCH, an admin status change, a de-attribution, the AI review and the POI enrichment write only if `status`/`updated_at` still match the row they read — a lost race returns 409 `conflict` (PATCH, admin) or retries (de-attribution) and deletes the objects it wrote, and a stale review writes nothing (its verdict write leaves `updated_at` alone). `@lib/community-checks` rebuilds every distance and climb from the coordinates (point km, length, display points, waypoint and variant km, 3 m-hysteresis climb) and drops client route breaks, POIs and `cumAscent`/`cumDescent`, so no client-claimed distance or climb is stored. The duplicate hash is sha256 of the trail without its `config`, so a rename does not get past it (the 409 carries `existingId` only for the caller's own route; the near-duplicate warning names the other route by id); a body whose non-GPX part exceeds 4 MB + 64 KB is refused 413 `trail_too_large` before it is checked; the 10-a-day `communitySubmit` limit is spent only after the checks pass and the stored JSON measures ≤ 4 MB, `communitySubmitAttempt` (30 a day) is spent by every submit before its body is parsed, and `communityEdit` (20 a day) by every PATCH that changes something. The `claude-sonnet-5-5` review (structured output, `fallbacks: 'default'`, all route text fenced as untrusted) runs from `waitUntil` (SDK client with a 20 s timeout and 1 retry) and **fails open** — `skipped` without the `ANTHROPIC_API_KEY` secret (`wrangler secret put ANTHROPIC_API_KEY`), `failed` on an API error or refusal. The review also sees a bounded sample of waypoint descriptions, the variant names, and a sample of off-trail and variant waypoint names (≤ 200 names in all, at least 50 of them off-trail/variant when there are that many). A reject with confidence ≥ 0.8, or 3 distinct reports filed after the route's last admin status change (`status_changed_at`) by accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`; younger accounts' reports are stored but do not count), hides an *unverified* route; a verified one stays up and rises to the top of the admin queue. An owner's detail of a hidden route (`GET /v1/me/community/routes`, or `GET /v1/community/routes/:id` with their token) carries `hiddenReason` (`'review' | 'reports' | 'admin'`). It is derived from the hide's `status_note`: the review and report hides write the fixed `REVIEW_HIDE_NOTE`/`REPORTS_HIDE_NOTE`, and anything else counts as an admin hide. `statusNote` itself stays admin-only, and an admin note equal to either fixed note is refused 400 `invalid_note`. Only an admin verifies. Deleting an account de-attributes its routes (CC0) rather than removing them; `deattribute_pending` keeps that durable, and a Cron Trigger (`*/15 * * * *`, `runCommunityMaintenance` in `src/index.ts`'s `scheduled`) retries pending de-attributions, re-runs AI reviews left `pending` over 10 minutes, and adds OSM POIs to routes that have none (see "community route POIs" below; on while `OVERPASS_ENDPOINTS` lists instances). A submit also adds the `region` check (`checkCommunityRegion`: a warning when the coordinates are in another country or state, never a change to the hiker's choice), and a PATCH that changes the region re-runs it. A PATCH re-runs the `metadata` check. Reports spend the `communityReport` bucket (20 a day) through `consumeRateLimit`. The public list and "my routes" are keyset-paged (`?cursor=` / `nextCursor`). A route an admin removed (or its owner deleted while an admin had it hidden) sets `blocks_resubmit`, refusing the same track again. Comments, plan sync and shared hiker waypoints take a community route's id as well as `ALLOWED_TRAILS` (next section).

## Comments API Worker: which trails (`workers/comments-api/src/trails.ts`)

`resolveTrail(env, trailId, use)` is the one trail gate for comments, plans, shared waypoints and the descriptions read. A trail is either curated (`ALLOWED_TRAILS`, held equal to the bundled trails by `scripts/server-trail-allowlist.test.ts`) or a community route (`isCommunityRouteId`, plus a row in `community_routes`: one primary-key read). Anything else — a `u_` import above all — is 400 (`invalid_trail`; `trail_not_allowed` for a plan). What a route takes depends on its status: a **public write** (`PUT /v1/comments/:id`, `PUT /v1/waypoints/:id`, a new share or an edit) needs a live route (`unverified`/`verified`), else 403 `trail_not_live`, so nothing new is published on a route nobody can see; a **private write** (`PUT /v1/plans/:id`) and the **reads** (`GET /v1/trails/:id/waypoints`, `/descriptions`) take any route the server has a row for, hidden or removed included — a plan is the hiker's own, and the phone keeps a route that was taken down ("No longer shared"); the feeds keep serving what was posted while it was up (the comment feeds never checked the trail). Deletes, reports and replays are not gated by trail. Rows are never deleted (removal is a tombstone), so "is a community route" is cached for the isolate's life and "is live" for `LIVE_CACHE_MS` (60 s, live results only): a hide stops new comments within a minute on every isolate, and a restore is read at once. The descriptions read answers an empty list for a route (its descriptions are in the route itself); the admin description PUT stays curated-only (`validateTrailId`).

## Comments API Worker: community route POIs (`workers/comments-api/`)

**On (Workers Paid).** `OVERPASS_ENDPOINTS` in `wrangler.toml` `[vars]` lists the instances; empty switches the enrichment off (routes are shared without POIs). It was shipped off and switched on once the account moved to Workers Paid (2026-10-20): its CPU (below) is far over Workers Free's 10 ms per invocation but well inside Paid's 15-minute cron limit, so a move back to Free means emptying it again. How it was turned on: apply migration `0009` (`npm run migrate:remote`), then set `OVERPASS_ENDPOINTS` to comma-separated https URLs — the list `wrangler.toml` suggests is `overpass-api.de`, `overpass.private.coffee`, `overpass.kumi.systems`, the three `INTERACTIVE_OVERPASS_ENDPOINTS` the phone uses — and `npm run deploy`. Every instance listed receives each live route's outline, so `docs/privacy-policy.md` and `public/privacy.html` name their operators; add an instance there before adding it here (`maps.mail.ru`, which `fetch-pois` sometimes needs, is deliberately not listed). Deploy order: migration first. Deployed without it, the enrichment logs `migration 0009 … is not applied` each run and does nothing (`isMissingPoiMigration`); nothing else reads the new columns.

**CPU on Workers Free.** Free allows 10 ms of CPU per invocation, cron included; waiting on Overpass is wall time and does not count, but what the run computes does, and it is well over 10 ms for any real route. `scripts/measure-community-poi-cpu.ts` (`npx tsx scripts/measure-community-poi-cpu.ts [trail-id …]`, after `npm run build:trails`) times each step on bundled trails standing in for community routes; on 2026-10-19 (Node, the same V8 as workerd; medians): Cape to Cape (0.5 MB stored JSON, 39 POIs) ~20 ms in all; Larapinta (1.2 MB) ~60 ms; the Heysen and the Bibbulmun (5-6 MB, more than the 4 MB a community route may be, so an upper bound) ~350-400 ms — parsing the stored JSON ~35 ms, planning the corridor ~200-270 ms (almost all `buildCorridorChunks`' Douglas-Peucker, the build's own), placing and finishing the real answer ~20-25 ms, re-encoding with its md5 ~65-80 ms. A synthetic answer at the enrichment's own cap (12,000 elements, ~1.8 MB) adds ~15 ms to parse and 140-260 ms to finish (mostly the duplicate and city-thinning passes; the placement itself goes through `createRouteIndex`, without which it alone took seconds). On Free the platform may stop the run at any of these points (the limit is enforced with some leniency, not reliably); on the Paid plan (30 s CPU by default) it fits with room to spare. What a stopped run costs is bounded: the claim is written before any work, so the attempt counts and the route is given up on after 4 (`failed`: shown without POIs, tried afresh 14 days later) rather than retried every hour; one stopped after writing its R2 objects but before its D1 write leaves a private JSON (and possibly a public copy) the row does not name — the private one is swept the next time the route is answered or given up on (`sweepPoiLeftovers`: everything under its private prefix the row does not name, older than the purge grace), and a public copy, content-addressed and listed nowhere, goes at the route's next republish (`purgeSuperseded`), hide or removal.

**What it does.** `enrichCommunityRoutePois` in `src/community.ts` is the third task of the `*/15` cron's `runCommunityMaintenance`, after the de-attribution retry and the stale-review re-run; `src/community-pois.ts` does the Overpass part. A submit stores the route without POIs (`runCommunityChecks` drops any the client sent; that stays so — POIs come only from the server) and never waits on Overpass. A later run asks Overpass for the POIs within 2 km of the route — main track, alternates and side trips — exactly as `scripts/fetch-pois.ts` and the phone do: `@lib/trail-poi-search` `planTrailPoiSearch` cuts it into the build's corridor queries (`@lib/osm-poi`/`@lib/poi-enrichment`, the `gpx-tools` port), and its `finishTrailPois` places the answers on the trail's km (`indexed`: the `createRouteIndex` grid) and runs the build's passes (noise, duplicates of the route's own waypoints, city thinning; no `TrailPoiConfig`, which a community route never has) and `slimPoi`. Only the HTTP is the worker's own (`queryOnce`), because it spends the run's budget. The trail JSON is then republished with a `pois` array, its config rebuilt as an edit rebuilds it (`withServerConfig`) with the OpenStreetMap credit in `dataSource` (`communityDataSource`: the hiker's part CC0, the POIs © OpenStreetMap contributors under the ODbL, linking openstreetmap.org/copyright; every later rebuild — an edit, a de-attribution — keeps it while the route has POIs): a new private and public object, `md5`/`bytes`/`updated_at` moved (phones see the md5 change and download it again; `updated_at` is the row's version and the public "updated" time of the JSON, which did change — `status_changed_at`, which the report count runs from, and the review are untouched), guarded on `status`/`updated_at` like an owner's edit (a lost race drops its objects and gives the attempt back), the old private object deleted and older public versions purged as after an edit. A route whose stored POIs come out unchanged is marked done without a rewrite. Because the POIs live in the canonical private JSON, every republish keeps them: an owner's edit and a de-attribution re-store from it, a restore republishes it. `content_hash` is never recomputed, so the duplicate check is unaffected. Backfill: migration `0009` makes every stored route due, so after it is switched on each live route is republished once with its POIs (a new md5 and `updated_at` each).

**Which routes, in what order.** `pois_due_at` alone decides (index `idx_community_routes_pois_due` on `(pois_due_at, created_at, id)` where it is set, which serves both the range and the order; the query keeps the planner off the status index with `+status`): `''` for a route never tried, an ISO time once an attempt has claimed it (an hour on; further after failures, see below), NULL once it has an answer or was skipped; a `failed` route is due again 14 days after it was given up on. Candidates are live routes (`unverified`/`verified`) due by now, untouched for 2 minutes and with no AI review `pending` (so the enrichment's write can never make a review lose its guard or push back the stale-review re-run), oldest due first, then oldest created — a route a run had to pass over keeps its place at the head of the next. 3 a run. Whatever changes a route's geometry in future must set `pois_due_at = ''` and `pois_attempts = 0` (and should drop the old `pois`); nothing does yet (replacing the GPX is a new submission).

**Budget and failure.** At most 20 Overpass requests a run across every route and endpoint (`POI_RUN_LIMITS`; Free allows 50 external subrequests an invocation, and the stale-review re-run may spend 10), 25 s Overpass `[timeout:]` with the request abandoned 5 s later, 1 s between requests — so one request takes at most `WORST_REQUEST_MS` (31 s), and every request must be able to finish within 6 minutes of the run's start. A route needing more than 10 corridor queries (`POI_LIMITS.maxQueriesPerRoute`, roughly 3,000-6,000 km; the Heysen takes 2) is `skipped`, never fetched in part; 10 × 31 s fits the 6 minutes, so any route that is fetched fits a fresh run however slow each answer is. A route is claimed (attempt counted, retry time set) before any work; it then starts only if all its missing answers fit what the run has left (requests and time, at the worst case each), else gives the attempt back untouched. Each answer is streamed under an 8 MB cap counted in bytes as received (`readCapped`: a declared `Content-Length` over it is refused unread, a chunked body is cancelled the moment it passes it); an answer over it, more than 12,000 distinct POIs fetched, more than 4,000 to ship, or a JSON over 4 MB makes the route `skipped`. Each answered query is cached in R2 beside the route's private copies (`community/private/<id>/overpass-<hash>.json`, the hash of the query salted with the route's id and `content_hash` — what stays put while the geometry does — so an owner's edit or a de-attribution, which rewrite the private copy, keep it usable; the content is public OSM data, so the key need not be secret; deleted once the route is answered or given up on). A route removed during an attempt stops it at the next answer (`PoiAnswerCache.put` re-reads the row and writes nothing for a removed route), and the private prefix is purged again afterwards in case an answer landed after the removal's own purge, so removal still leaves neither prefix behind, so a later attempt asks only for what is missing. A query goes to the instance that answered last, then the others; a 429 or 503 with `Retry-After` is honoured — that instance is left alone for the time asked, and the run waits for the first one free when every other has failed or is waiting, if the wait is at most 60 s and still leaves time for the route's remaining queries — and a longer `Retry-After` benches the instance for the rest of the run. **Fails open**: an attempt that ends without every answer stores nothing on the route, which stays as it is, without POIs. What happens next depends on why (`PoiFailure`): **an outage never uses up a route's attempts** — a network error, a timeout, a 5xx, a 408 or 429, a `runtime error` remark or a page that is not JSON gives the attempt back, and the route backs off instead (`pois_failures` consecutive failures: due again 1 h, 2 h, 4 h … after the attempt, capped at 2 days by `poiBackoffMs`; reset by an answer), so even a week-long outage of every instance (all three were unreachable from a cloud session on 2026-09-30, see `build-scripts.md`) costs each route a few requests a day and recovers by itself. Only a failure tied to the route counts: an HTTP 4xx other than 408/429 (Overpass refusing its query), its stored copy missing, or the platform stopping the run while on it (the claim, never recorded). Those back off the same way; the 4th marks the route `failed`, with its attempts reset and due again 14 days later (`failedRetryAfterMs`), so no state needs a hand-run SQL fix. An attempt that only ran out of the run's budget, lost a race with an edit, or met a removal is given back without backing off. A route too long, with too many POIs or too large a JSON is `skipped` for its geometry, for good. `pois_error` records why (`run_budget`, `rate_limited`, `overpass: <host>: <error>; …`, `route_too_long`, `too_many_pois`, `trail_too_large`, `route_changed`, `gave_up`).

**Not kept across attempts, and why:** a partial set of POIs is never published (a route would look as if it had nothing on the stretch that failed); the per-query cache is what carries progress, and it lives only until the route is answered.

## Comments API Worker: comment targets and limits (`workers/comments-api/`)

A comment's `waypointId` is checked by its prefix (`validateCommentTarget` in `src/validation.ts`, over `@lib/comment-targets`), and the kind must fit the trail's: `w_` + 8-40 hex (the curated registry; curated trails only), `uw_` + 1-40 lowercase alphanumerics with an optional `_<n>` (a community route's own waypoints, the ids its import minted and the server stored as submitted; `c_` routes only — form only, like the curated ids: the worker carries neither the registry, a route's stored trail nor the POI lists, so a route whose file holds some other id for a place takes no comments on it, and the phone offers no composer there), `hw_` + a lowercase v4 uuid (must be a shared waypoint the server holds on that trail: 404 `waypoint_not_found` if not, 410 `waypoint_deleted` once tombstoned), or `osm_<node|way|relation>_<safe integer>` (`poiCommentId`). Anything else is 400 `invalid_waypoint`, since no screen would show it. `test/comment-guards.test.ts` holds every id in `data/waypoint-ids.json` to it. The phone's drain holds a comment on the hiker's own `hw_` waypoint while that waypoint's share is still pending or in flight (`outboxRepo.hasPending`; gated like a photo on its comment, re-checked pass after pass until a pass sends nothing). A share that failed is not waited on: the comment goes and takes the 404. A replay of a stored comment is answered before the body is validated, and a request that loses the insert race to its own replay hands its rate-limit unit back (`refundRateLimit`). Plans and curated descriptions still take the looser `^[a-z0-9_-]{4,64}$`. Every rate limit, the comment post (60 a day) and comment report (20 a day) limits included, goes through `consumeRateLimit` in `src/rate-limit.ts`; never count a table's rows and insert after, which a parallel burst gets past.

## Comments API Worker: shared hiker waypoints (`workers/comments-api/`)

`src/shared-waypoints.ts` (migration `0007`): D1 `shared_waypoints` + `shared_waypoint_reports`. `PUT /v1/waypoints/:id` creates (the client-minted `hw_` id is the idempotency key) or is the owner's edit — an identical PUT is a replay that leaves `updated_at` alone; one its owner deleted (made private) is revived by the owner's next PUT, under the same id; one an admin or reports hid answers 410; every write stamps `updated_at` just before the statement that commits it, so a concurrent delta read cannot get ahead of it; `sharedWaypointCreate` (20 a day) and `sharedWaypointEdit` (60) rate buckets. `DELETE` is owner or admin. `POST /v1/waypoints/:id/report` is one per reporter (`sharedWaypointReport`, 20 a day; not your own), the first qualifying one starts the automated review ("comment and waypoint review" below), which may tombstone it at once, and `USER_WAYPOINT_LIMITS.reportsToHide` (3) distinct reporters tombstone it whatever the review said (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`) and only reports filed after the last admin restore (`restored_at`). `POST /v1/admin/waypoints/:id/restore` undoes an admin or report hide (not an owner's delete). `GET /v1/trails/:trailId/waypoints?since=` is the public full/delta read (tombstones in delta mode, 2,000 rows a page, keyset-paged by `(updated_at, id)` through `nextCursor` like the comments feed); a token, when sent, adds `mine`. `GET /v1/admin/waypoints` lists them reported first. The trail must be curated or a live community route (`resolveTrail`; the listing takes a hidden one too), so imports keep their waypoints private. Deleting an account tombstones its shared waypoints, as it does its comments.

## Comments API Worker: comment moderation (`workers/comments-api/`)

`src/reports.ts`, `src/comments.ts`, `src/moderation.ts` (migration `0008`, which rebuilds `comments` and `comment_reports` because SQLite cannot widen a CHECK — dropping a referenced table fails D1's foreign-key check even deferred, so the pair is rebuilt together). Comments are moderated like shared waypoints: the first qualifying report starts the automated review (next section), which may hide one at once, and `COMMENT_REPORTS_TO_HIDE` (3) distinct reporters tombstone one whatever it said (`deleted_by = 'reports'`), counting only accounts at least 24 h old when they reported (`REPORTER_MIN_ACCOUNT_AGE_MS`), never the author, and only reports filed after the last admin restore (`restored_at`). A report hide keeps the photos; `POST /v1/admin/comments/:id/restore` undoes it (the restore reaches the author's phone through the public `GET /v1/trails/:trailId/comments?since=` feed, which, like the waypoints feed, adds `mine` to live rows when a token is sent — a bad or expired token reads as anonymous, and a token-bearing response is `Cache-Control: private, no-store`), and an owner's or admin's `DELETE` (or account deletion) makes it final and purges them (from R2 and from `photo_urls_json`) — an owner or admin delete cannot be restored. `GET /v1/admin/comments?reported=1` and `GET /v1/admin/waypoints` carry every report (reason, detail, reporter) and whether the author is banned. `POST /v1/admin/users/:id/ban` `{ banned, removeContent? }` bans or unbans (never an admin); `removeContent` admin-deletes the account's comments and shared waypoints. A ban sets `users.banned_at`; account deletion sets `is_banned` and `users.deleted_at`, and a deleted account can never be unbanned (the migration backfills both columns: deleted accounts by their fixed display name and revoked tokens, every other banned account as banned). The admin listings carry `userBanned`, `userAdmin` and `userDeleted`, so the page offers only the ban actions the server will take. Every tombstone the ban writes is stamped after its reads, just before the batch that commits it. The admin page is `src/web/admin-moderation.html` (unlinked, noindex, client `src/web/api/moderation.ts`).

## Comments API Worker: comment and waypoint review (`workers/comments-api/`)

`src/content-review.ts` (migration `0010`: `review_status`, `review_json`, `review_requested_at` on `comments` and `shared_waypoints`, plain added columns so neither table is rebuilt). Its job is to take clearly bad or malicious posts down after **one** report rather than three. Two triggers claim a review (`claimContentReview`, one `UPDATE … RETURNING`, so concurrent reports claim it once; the claim leaves `updated_at` alone, so phones do not re-sync):

- **A report** (`reviewOnReport`, from `ctx.waitUntil` in `reportComment` / `reportSharedWaypoint`): needs at least one qualifying report (account a day old when it reported, not the author, since `restored_at`). It claims a post never reviewed, one whose review `failed`, or one reviewed only because of the screen (so the report's words are weighed); a `done` report review is never asked again, and later reports only count towards the three-report backstop.
- **The screen** (`screenOnPost`, from `waitUntil` after a comment is created with text, and after a shared waypoint is created, revived or edited): Llama Guard 3 (`@cf/meta/llama-guard-3-8b` on the `AI` binding) reads the comment text, or the waypoint's name and description. A flag in `SCREEN_CATEGORIES` (S1-S12 minus S6 specialised advice, which is all hiking advice, and S13 elections) claims a review; the screen never hides anything itself. An owner's waypoint edit resets the review columns (the old verdict was about the old text) and screens the new text.

`reviewContent` sends the post (comment: text, water status, observed time, photo **count**, place id; waypoint: name, type, description, position) and the newest five reports' reason and note to `REVIEW_MODEL` (`claude-sonnet-5-5`, structured output, effort low, the same SDK settings as the route review), fenced in `<post>` with `<`/`>` escaped. Never photos, display names or account data. Verdicts `remove` / `needs_human` / `keep` with a confidence and categories; `remove` at `CONTENT_REVIEW_HIDE_CONFIDENCE` (0.85) or above tombstones the post as `deleted_by = 'reports'` with `review.hid = true` (the same provisional hide an admin restores or makes final, so `DeletedBy` and the phones are unchanged). The write and the hide are one batch guarded by the `updated_at` read before the call: an owner edit, a three-report hide or an admin action meanwhile wins, and the review stays `pending` for the cron. It **fails open**: no key, an API error, a refusal or an unusable answer is `failed` and hides nothing. A post an admin restored (`restored_at` set) is never claimed again, so only reporters can hide it after that. Water-only comments (no text) are never reviewed. The `*/15` cron runs `rerunStaleContentReviews`: up to `STALE_CONTENT_REVIEW_BATCH` (5) per table still `pending` `STALE_CONTENT_REVIEW_AFTER_MS` (2 min) after their claim (a `waitUntil` cut short; the review's timeout plus one retry can outlast its ~30 s).

Admin: `GET /v1/admin/comments?reported=1` lists reported **or reviewed** comments (a screen-flagged one may have no report; the partial index `idx_comments_review` serves that arm), hidden first, then those the review would `remove` or wants a human for, then by report count; `GET /v1/admin/waypoints` orders the same way. Both carry `review` (`ContentReview` in `@lib/comments-api-types`), which `src/web/admin-moderation.ts` shows ("Hidden by the automated review", the verdict, confidence, categories, summary and trigger).

Without `ANTHROPIC_API_KEY` nothing is screened or reviewed and comments and waypoints are hidden by three reporters only. Tests run with `remoteBindings: false` (`vitest.config.mts`) and no key, so the binding is never called; the review tests inject a fake client and a fake `AI`.

**Setup outside the code** (dashboard; none of it is needed for the review to work):

1. **AI Gateway** (logs, spend and rate limits for every model call, Anthropic and Workers AI). Create a gateway (Cloudflare dashboard → AI → AI Gateway) and set `AI_GATEWAY_ID` in `wrangler.toml` to its name; empty means calls go straight to the provider. If it is an Authenticated Gateway (the auto-created `default` gateway is), create a token and `wrangler secret put AI_GATEWAY_TOKEN`, or every Anthropic call fails (the review then records `failed` and hides nothing). The gateway logs request bodies by default, which hold the reported text: set a short log retention, or turn off body logging, to keep it no longer than D1 does. A gateway URL that cannot be resolved falls back to the direct API.
2. **CSAM Scanning Tool** (photos are not reviewed by any model). Cloudflare dashboard → Caching → Configuration → CSAM Scanning Tool, for the zone serving `PHOTOS_PUBLIC_BASE` (`data.contour-map-tiles.net`); it needs a verified notification email. It scans images served through Cloudflare's cache, so check in the dashboard that it covers the R2 custom domain.
3. **Workers AI** needs no setup on Workers Paid; Llama Guard is billed per request (one per new comment with text, and per waypoint create or edit).

## Comments API Worker: plan documents (`workers/comments-api/`)

`src/plans.ts` (migration `0004`): D1 `plans` holds each `PlanDocument` whole in `document_json`, so a new document field needs no migration — but `validatePlanDocument` (`src/validation.ts`) rebuilds the stored document **field by field**, so a field it does not name is silently dropped on `PUT /v1/plans/:id` and lost on the next sync. A new field therefore ships as a worker change first (validated, then copied onto `document`), deployed before any client sends it. Each field is refused with a 400 (`planError`) rather than trimmed. `resupplyZeroDays` (zero days per resupply stop, by option id) is checked against `PLAN_LIMITS.resupplyZeroDaysMax` (500 entries), keys against the waypoint-id pattern (4-64 of `[a-z0-9_-]`) and values with `@lib/plan-types` `isStoredZeroDays` (half-day steps, 0.5 to `zeroDaysMax` 14) — `invalid_resupply_zero_days`; an empty map is stored as none.

## Contour Tile Worker (`workers/contour-tiles/`)

Cloudflare Worker serving contour vector tiles from PMTiles on R2. URL pattern: `/{source}/{z}/{x}/{y}.pbf`. Uses R2 bucket `aus-map-data`: source `world` serves `contours/world.pmtiles` (Copernicus GLO-30), and `contours` is an alias of it, kept because shipped Tracknotes builds request `/contours/…` for Australian trails and read `/health`'s top-level `ok` (which follows `DEFAULT_SOURCE`, `world`). PMTiles instances are cached per R2 key, so the two names share one. Until #228 `contours` served `contours/australia.pmtiles` (Geoscience Australia DEM-S); that archive stays in R2 as a frozen public download (last built 2026-10-23) but is no longer served or rebuilt. Repointing a source needs a purge of its edge-cached URLs (`tiles.contour-map-tiles.net/contours/*` after this one). Built with `wrangler`; details in `workers/contour-tiles/README.md`.
